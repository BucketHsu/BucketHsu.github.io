本篇整合 Nginx 常用觀念與實務設定，包含反向代理、路徑轉換、Template / Include、HTTPS、負載平衡、錯誤頁、安全設定與排查方式。

範例皆使用通用網域、loopback 或示意私有網段，不包含實際專案名稱、內網 IP、主機名稱或其他環境識別資訊。

== Nginx 是什麼

Nginx 常被放在系統最前面，負責接收使用者請求，再決定要直接回傳靜態檔案，或把請求轉送到 Spring Boot、Tomcat、Node.js 等後端服務。

常見用途：

* 提供 HTML、CSS、JavaScript、圖片等靜態檔案。
* 作為 Reverse Proxy（反向代理）。
* 集中管理 HTTPS 憑證。
* 依網域或 URL 路徑分流。
* 將流量分散到多台後端。
* 統一處理 Header、壓縮、快取、錯誤頁與 Log。

[plantuml,nginx-reverse-proxy-flow,svg]
----

可以把 Nginx 想成系統的「入口櫃台」：使用者只知道 Nginx，不需要知道真正後端在哪裡。

== 設定檔結構與 Request 判斷流程

典型設定由 `http`、`server`、`location` 等層級組成：

[source,nginx]
----
http {
    server {
        listen 443 ssl;
        server_name example.com;

        location /api/ {
            proxy_pass http://127.0.0.1:8080;
        }
    }
}
----

[cols="25%,75%",options="header"]
|===
|Context |用途

|Main
|程序、Worker、PID、全域 Log。

|`events`
|連線處理。

|`http`
|HTTP / HTTPS 共用設定、Log、gzip、upstream。

|`server`
|依監聽 port 與網域定義虛擬主機。

|`location`
|依 URL 路徑決定如何處理請求。

|`upstream`
|定義一組後端伺服器。
|===

=== Request 進來後怎麼判斷

[source,text]
----
Request
  ↓
listen / server_name
找到對應 server
  ↓
location
找到最適合的路徑規則
  ↓
├─ root / alias      → 直接讀靜態檔案
├─ proxy_pass        → 轉送後端
└─ return / rewrite  → 直接回應或重新導向
----

排查時依這個順序往下看，通常比直接從整份 `nginx.conf` 找問題快很多。

== 安裝與常用管理指令

=== Linux

[source,bash]
----
sudo apt install nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

# 驗證設定
sudo nginx -t

# 顯示 include 展開後的完整設定
sudo nginx -T

# 套用設定
sudo systemctl reload nginx
----

=== Windows

[source,powershell]
----
cd C:\nginx
.\nginx.exe
.\nginx.exe -t
.\nginx.exe -s reload
.\nginx.exe -s quit
----

[NOTE]
====
正式環境通常使用 Linux + systemd；Windows 版較適合測試、內部工具或既有 Windows 部署環境。
====

== 靜態網站、`root`、`alias` 與 SPA

=== `root`

[source,nginx]
----
location /files/ {
    root /data;
}
----

請求：

[source,text]
----
/files/manual.pdf
----

實際檔案：

[source,text]
----
/data/files/manual.pdf
----

=== `alias`

[source,nginx]
----
location /downloads/ {
    alias /data/files/;
}
----

請求 `/downloads/manual.pdf` 會讀取 `/data/files/manual.pdf`。

`root` 是「把 URI 接在 root 後面」，`alias` 則是「用指定目錄取代 location 前綴」。

=== SPA

React、Vue、Angular 等 SPA 常見：

[source,nginx]
----
location / {
    root /var/www/frontend;
    try_files $uri $uri/ /index.html;
}
----

如果不是 SPA，不建議所有 404 都回 `index.html`。

== 反向代理基本設定

[source,nginx]
----
location /api/ {
    proxy_pass http://127.0.0.1:8080;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
----

[cols="35%,65%",options="header"]
|===
|設定 |用途

|`proxy_pass`
|指定後端服務。

|`Host`
|保留原始網域。

|`X-Real-IP`
|傳遞直接連到 Nginx 的來源 IP。

|`X-Forwarded-For`
|保留經過多層 Proxy 的來源 IP 鏈。

|`X-Forwarded-Proto`
|告知後端原始請求是 HTTP 或 HTTPS。
|===

== `location` 與 `proxy_pass` 路徑規則

這是 Nginx 最容易混淆的地方之一。

=== 先記一個核心規則

[source,text]
----
Request: /api/users

location /api/ {
    proxy_pass http://backend;
}
        ↓
Backend: /api/users

--------------------------------

location /api/ {
    proxy_pass http://backend/;
}
        ↓
Backend: /users

--------------------------------

location /api/ {
    proxy_pass http://backend/internal/;
}
        ↓
Backend: /internal/users
----

簡單記法：

* `proxy_pass http://backend;`：沒有 URI 部分，通常保留完整原始 URI。
* `proxy_pass http://backend/;`：以 `/` 取代匹配到的 `/api/`。
* `proxy_pass http://backend/internal/;`：以 `/internal/` 取代 `/api/`。

=== `location /api` 與 `/api/`

`location /api` 可能連 `/apitest` 都一起匹配；如果代表一個 URL 目錄，通常建議：

[source,nginx]
----
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
----

若需要把 `/api` 明確導到 `/api/`：

[source,nginx]
----
location = /api {
    return 301 /api/;
}

location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
----

== 對外路徑與後端 Context Path 不同

有時候 Nginx 對外使用一個路徑，但後端應用程式仍維持另一個 Context Path。

例如：

[source,text]
----
瀏覽器： /application-test/
後端：   /application/
----

=== 只改 `proxy_pass` 為什麼可能不夠

[source,nginx]
----
location /application-test/ {
    proxy_pass http://127.0.0.1:8080/application/;
}
----

Request 確實可以正確轉成：

[source,text]
----
/application-test/user
        ↓
/application/user
----

但後端仍可能回：

[source,http]
----
Set-Cookie: JSESSIONID=...; Path=/application
Location: /application/login
----

瀏覽器只知道 `/application-test/`，因此 Cookie 或 Redirect 可能跑回錯的路徑。

=== 完整改寫

[source,nginx]
----
location /application-test/ {
    # Request 路徑
    proxy_pass http://127.0.0.1:8080/application/;

    # Cookie Path
    proxy_cookie_path /application /application-test;

    # 相對 Redirect
    proxy_redirect /application/ /application-test/;

    # 完整 URL Redirect
    proxy_redirect ~^https?://[^/]+/application/(.*)$ /application-test/$1;
}
----

[plantuml,nginx-context-path-rewrite,svg]
----
@startuml
left to right direction

actor Browser
rectangle Nginx
rectangle App as "Application Server\nContext Path: /application/"

Browser -> Nginx : GET /application-test/page
Nginx -> App : GET /application/page
App --> Nginx : Location: /application/login\nSet-Cookie: Path=/application
Nginx --> Browser : Location: /application-test/login\nSet-Cookie: Path=/application-test
@enduml
----

=== 最簡單的方式

如果後端 Context Path 可以調整，最好讓前後端一致：

[source,text]
----
外部： /application-test/
後端： /application-test/
----

如此通常不需要 `proxy_cookie_path` 與 `proxy_redirect`，設定較單純。

== Template、Include 與設定檔拆分

設定不要全部塞在一個檔案，但也不需要拆得過度零碎。常見做法是：

[source,text]
----
/etc/nginx/
├── nginx.conf
├── conf.d/
│   └── site.conf
└── snippets/
    └── proxy-common.conf
----

`nginx.conf` 負責全域與 include；`site.conf` 負責站台；`proxy-common.conf` 放多個 location 共用的 Proxy 設定。

=== Include

[source,nginx]
----
http {
    include /etc/nginx/conf.d/*.conf;
}
----

`include` 是 Nginx 啟動或 reload 時，把其他設定檔載入目前 context。

=== Template

Template 適合容器環境依環境變數產生正式 `.conf`：

[source,nginx]
----
server {
    listen 443 ssl;
    server_name ${SERVER_NAME};

    location /api/ {
        proxy_pass http://${BACKEND_HOST}:${BACKEND_PORT};
    }
}
----

官方 Nginx Container 常見：

[source,text]
----
/etc/nginx/templates/site.conf.template
        ↓ entrypoint / envsubst
/etc/nginx/conf.d/site.conf
        ↓ include
Nginx
----

[plantuml,nginx-template-flow,svg]
----
@startuml
left to right direction

rectangle Env as "Environment Variables"
rectangle Template as "site.conf.template"
rectangle Entry as "Entrypoint / envsubst"
rectangle Conf as "site.conf"
rectangle Nginx

Env --> Entry
Template --> Entry
Entry --> Conf : 產生
Conf --> Nginx : include / 載入
@enduml
----

重點：

* Template：先「產生」設定檔。
* Include：Nginx 再「載入」設定檔。
* `.template` 通常不是 Nginx 最終直接解析的檔案。

== HTTPS 與 TLS Termination

[source,nginx]
----
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/private.key;
    ssl_protocols TLSv1.2 TLSv1.3;
}

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
----

[plantuml,nginx-tls-termination-flow,svg]
----
@startuml
left to right direction

actor User as "瀏覽器"
rectangle Nginx as "Nginx\nTLS / Certificate"
rectangle App as "Application\nSpring Boot / Tomcat"

User -> Nginx : HTTPS :443
Nginx -> App : HTTP :8080\n或內部 HTTPS
App --> Nginx : Response
Nginx --> User : HTTPS Response
@enduml
----

由 Nginx 統一處理 TLS 的作法稱為 TLS Termination。後端通常靠 `X-Forwarded-Proto` 得知原始連線是否為 HTTPS。

[NOTE]
====
Nginx 到後端是否能使用 HTTP，要依網路邊界與資安要求決定；跨主機、跨網段或零信任環境可能仍需內部 HTTPS。
====

== 負載平衡

[source,nginx]
----
upstream backend_servers {
    least_conn;
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    keepalive 32;
}

location /api/ {
    proxy_pass http://backend_servers;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}
----

[plantuml,nginx-load-balancing-flow,svg]
----
@startuml
left to right direction

actor User
rectangle Nginx
rectangle A as "Backend A\n10.0.0.11:8080"
rectangle B as "Backend B\n10.0.0.12:8080"

User -> Nginx : Request
Nginx --> A : Request 1
Nginx --> B : Request 2
A --> Nginx : Response
B --> Nginx : Response
Nginx --> User : Response
@enduml
----

`upstream` 定義後端群組，`proxy_pass http://backend_servers;` 則把請求交給這組服務。

== WebSocket、SSE、Timeout 與上傳限制

=== WebSocket

[source,nginx]
----
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

location /socket/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
}
----

=== SSE / 串流

[source,nginx]
----
location /events/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_buffering off;
    proxy_cache off;
}
----

=== Timeout 與上傳

[source,nginx]
----
location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_connect_timeout 10s;
    proxy_send_timeout 60s;
    proxy_read_timeout 60s;
}

client_max_body_size 100m;
----

`413 Request Entity Too Large` 時需同時檢查 Nginx 與後端應用程式的上傳限制。

== 安全 Header、CORS 與存取控制

=== 常見安全 Header

[source,nginx]
----
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
----

若要啟用 HSTS：

[source,nginx]
----
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
----

[WARNING]
====
啟用 `includeSubDomains` 前，必須確認所有子網域皆支援 HTTPS。
====

=== CORS

CORS 建議由單一層負責，避免後端與 Nginx 重複加入 Header。

[source,nginx]
----
location /api/ {
    add_header Access-Control-Allow-Origin "https://frontend.example.com" always;
    proxy_pass http://127.0.0.1:8080;
}
----

若使用 Cookie 或認證資訊，`Access-Control-Allow-Origin` 不可設為 `*`。

=== IP 白名單

[source,nginx]
----
location /admin/ {
    allow 192.168.1.0/24;
    deny all;
}
----

=== Basic Authentication

[source,nginx]
----
location /private/ {
    auth_basic "Restricted";
    auth_basic_user_file /etc/nginx/.htpasswd;
}
----

Basic Auth 應搭配 HTTPS。

== 自訂錯誤頁與 `proxy_intercept_errors`

最常見的做法是由 Nginx 統一顯示 404、502、503、504 等錯誤頁。

[source,nginx]
----
error_page 404 /404.html;
error_page 502 503 504 /500.html;

location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_intercept_errors on;
}

location = /404.html {
    root /usr/share/nginx/html;
    internal;
}

location = /500.html {
    root /usr/share/nginx/html;
    internal;
}
----

`error_page` 定義「哪些狀態要怎麼處理」，`proxy_intercept_errors on` 則決定是否攔截 upstream 的錯誤回應套用這些規則。

[plantuml,nginx-error-flow,svg]
----
@startuml
left to right direction

actor Browser as "瀏覽器"
participant Nginx
participant Upstream as "upstream"

Browser -> Nginx : Request
Nginx -> Upstream : Proxy Request
Upstream --> Nginx : HTTP status / Response

alt 符合 error_page 且 proxy_intercept_errors on
    Nginx -> Nginx : 套用自訂錯誤頁
    Nginx --> Browser : 自訂錯誤頁
else 其他情況
    Nginx --> Browser : upstream 原始回應
end
@enduml
----

公開錯誤頁不要顯示 Stack Trace、SQL、內部 IP、Framework 版本、實體路徑或內部專案名稱。

== Log 與問題排查

=== 建議 Log 格式

[source,nginx]
----
log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                'request_time=$request_time '
                'upstream_time=$upstream_response_time';

access_log /var/log/nginx/access.log main;
error_log /var/log/nginx/error.log warn;
----

重要欄位：

* `$status`：HTTP 狀態碼。
* `$request_time`：Nginx 處理整個請求的時間。
* `$upstream_response_time`：等待後端回應的時間。

=== 常見狀態碼

[cols="18%,32%,50%",options="header"]
|===
|狀態碼 |常見原因 |排查方向

|403
|權限、deny、SELinux
|檢查檔案權限與存取規則。

|404
|location、root、alias、URI 錯誤
|確認 Request 路徑與實體路徑。

|413
|Request Body 過大
|檢查 `client_max_body_size` 與後端限制。

|499
|用戶端提前中斷
|檢查前端 timeout、網路與後端處理時間。

|502
|無法連後端或 upstream 異常
|檢查程序、IP、port、防火牆與 Log。

|504
|後端回應逾時
|檢查後端效能與 `proxy_read_timeout`。
|===

=== 用 `curl` 驗證

[source,bash]
----
# 看 Header 與 Redirect
curl -I https://example.com/application-test/

# 看完整 Response
curl -i https://example.com/api/users

# 確認重新導向
curl -IL https://example.com/application-test/
----

若是 Context Path、Cookie 或 Redirect 問題，應同時檢查：

* Request URL。
* Response `Location`。
* Response `Set-Cookie` 的 `Path`。
* 後端實際收到的 URI。

== 公開 Repository 的安全檢查

公開 Nginx 文件或設定範例應移除：

* 真實公網或私網 IP。
* 實際網域與內部 DNS。
* 專案代碼與系統名稱。
* Container / VM / Pod 真實名稱。
* Cookie 真實名稱。
* 憑證組織資訊。
* 帳號、密碼、Token、Basic Auth 內容。
* Log 中的使用者識別資料。

推薦以 `example.com`、`127.0.0.1`、`10.0.0.x`、`application`、`backend-a` 等通用名稱取代。

== 正式環境檢查清單

* `nginx -t` 驗證成功。
* `nginx -T` 確認 include 展開結果。
* DNS、防火牆、後端 port 正確。
* HTTPS 憑證與完整憑證鏈正確。
* Proxy Header 正確。
* Context Path、Cookie Path、Redirect 已實際測試。
* Timeout 與上傳限制符合需求。
* Log 有輪替與容量管理。
* CORS、HSTS、安全 Header 經過測試。
* 錯誤頁不洩漏內部資訊。
* 設定有備份與 rollback 方法。
