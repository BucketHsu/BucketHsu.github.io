本篇整合 Nginx 常用觀念與實務設定，包含反向代理、路徑轉換、Template / Include、HTTPS、負載平衡、錯誤頁、安全設定與排查方式。

範例皆使用通用網域、loopback 或示意私有網段，不包含實際專案名稱、內網 IP、主機名稱或其他環境識別資訊。

== Nginx 是什麼

Nginx 常被放在系統最前面，負責接收使用者請求，再決定要直接回傳靜態檔案，或把請求轉送到 Spring Boot、Tomcat、Node.js 等後端服務。

常見用途：

* 提供 HTML、CSS、JavaScript、圖片等靜態檔案。
* 作為 Reverse Proxy（反向代理）。
* 集中管理 HTTPS 憑證。
* 依網域或 URL 路徑分流。
* 將流量分散到多台後端。
* 統一處理 Header、壓縮、快取、錯誤頁與 Log。

== 設定檔結構與 Request 判斷流程

典型設定由 `http`、`server`、`location` 等層級組成：

[source,nginx]
----
http {
    server {
        listen 443 ssl;
        server_name example.com;

        location /api/ {
            proxy_pass http://127.0.0.1:8080;
        }
    }
}
----

[cols="25%,75%",options="header"]
|===
|Context |用途

|Main
|程序、Worker、PID、全域 Log。

|`events`
|連線處理。

|`http`
|HTTP / HTTPS 共用設定、Log、gzip、upstream。

|`server`
|依監聽 port 與網域定義虛擬主機。

|`location`
|依 URL 路徑決定如何處理請求。

|`upstream`
|定義一組後端伺服器。
|===

=== Request 進來後怎麼判斷

[source,text]
----
Request
  ↓
listen / server_name
找到對應 server
  ↓
location
找到最適合的路徑規則
  ↓
├─ root / alias      → 直接讀靜態檔案
├─ proxy_pass        → 轉送後端
└─ return / rewrite  → 直接回應或重新導向
----

排查時依這個順序往下看，通常比直接從整份 `nginx.conf` 找問題快很多。

== 靜態網站、`root`、`alias` 與 SPA

=== `root`

[source,nginx]
----
location /files/ {
    root /data;
}
----

請求：

[source,text]
----
/files/manual.pdf
----

實際檔案：

[source,text]
----
/data/files/manual.pdf
----

=== `alias`

[source,nginx]
----
location /downloads/ {
    alias /data/files/;
}
----

請求 `/downloads/manual.pdf` 會讀取 `/data/files/manual.pdf`。

`root` 是「把 URI 接在 root 後面」，`alias` 則是「用指定目錄取代 location 前綴」。

=== SPA

React、Vue、Angular 等 SPA 常見：

[source,nginx]
----
location / {
    root /var/www/frontend;
    try_files $uri $uri/ /index.html;
}
----

如果不是 SPA，不建議所有 404 都回 `index.html`。

== 反向代理基本設定

[source,nginx]
----
location /api/ {
    proxy_pass http://127.0.0.1:8080;

    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
----

[cols="35%,65%",options="header"]
|===
|設定 |用途

|`proxy_pass`
|指定後端服務。

|`Host`
|保留原始網域。

|`X-Real-IP`
|傳遞直接連到 Nginx 的來源 IP。

|`X-Forwarded-For`
|保留經過多層 Proxy 的來源 IP 鏈。

|`X-Forwarded-Proto`
|告知後端原始請求是 HTTP 或 HTTPS。
|===

== `location` 與 `proxy_pass` 路徑規則

這是 Nginx 最容易混淆的地方之一。

=== 先記一個核心規則

[source,text]
----
Request: /api/users

location /api/ {
    proxy_pass http://backend;
}
        ↓
Backend: /api/users

--------------------------------

location /api/ {
    proxy_pass http://backend/;
}
        ↓
Backend: /users

--------------------------------

location /api/ {
    proxy_pass http://backend/internal/;
}
        ↓
Backend: /internal/users
----

簡單記法：

* `proxy_pass http://backend;`：沒有 URI 部分，通常保留完整原始 URI。
* `proxy_pass http://backend/;`：以 `/` 取代匹配到的 `/api/`。
* `proxy_pass http://backend/internal/;`：以 `/internal/` 取代 `/api/`。

=== `location /api` 與 `/api/`

`location /api` 可能連 `/apitest` 都一起匹配；如果代表一個 URL 目錄，通常建議：

[source,nginx]
----
location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
----

若需要把 `/api` 明確導到 `/api/`：

[source,nginx]
----
location = /api {
    return 301 /api/;
}

location /api/ {
    proxy_pass http://127.0.0.1:8080;
}
----

== 對外路徑與後端 Context Path 不同

有時候 Nginx 對外使用一個路徑，但後端應用程式仍維持另一個 Context Path。

例如：

[source,text]
----
瀏覽器： /application-test/
後端：   /application/
----

=== 只改 `proxy_pass` 為什麼可能不夠

[source,nginx]
----
location /application-test/ {
    proxy_pass http://127.0.0.1:8080/application/;
}
----

Request 確實可以正確轉成：

[source,text]
----
/application-test/user
        ↓
/application/user
----

但後端仍可能回：

[source,http]
----
Set-Cookie: JSESSIONID=...; Path=/application
Location: /application/login
----

瀏覽器只知道 `/application-test/`，因此 Cookie 或 Redirect 可能跑回錯的路徑。

=== 完整改寫

[source,nginx]
----
location /application-test/ {
    # Request 路徑
    proxy_pass http://127.0.0.1:8080/application/;

    # Cookie Path
    proxy_cookie_path /application /application-test;

    # 相對 Redirect
    proxy_redirect /application/ /application-test/;

    # 完整 URL Redirect
    proxy_redirect ~^https?://[^/]+/application/(.*)$ /application-test/$1;
}
----

[plantuml,nginx-context-path-rewrite,svg]
----
@startuml
left to right direction

actor Browser
rectangle Nginx
rectangle App as "Application Server\nContext Path: /application/"

Browser -> Nginx : GET /application-test/page
Nginx -> App : GET /application/page
App --> Nginx : Location: /application/login\nSet-Cookie: Path=/application
Nginx --> Browser : Location: /application-test/login\nSet-Cookie: Path=/application-test
@enduml
----

=== 最簡單的方式

如果後端 Context Path 可以調整，最好讓前後端一致：

[source,text]
----
外部： /application-test/
後端： /application-test/
----

如此通常不需要 `proxy_cookie_path` 與 `proxy_redirect`，設定較單純。

== Template、Include 與設定檔拆分

設定不要全部塞在一個檔案，但也不需要拆得過度零碎。常見做法是：

[source,text]
----
/etc/nginx/
├── nginx.conf
├── conf.d/
│   └── site.conf
└── snippets/
    └── proxy-common.conf
----

`nginx.conf` 負責全域與 include；`site.conf` 負責站台；`proxy-common.conf` 放多個 location 共用的 Proxy 設定。

=== Include

[source,nginx]
----
http {
    include /etc/nginx/conf.d/*.conf;
}
----

`include` 是 Nginx 啟動或 reload 時，把其他設定檔載入目前 context。

=== Template

Template 適合容器環境依環境變數產生正式 `.conf`：

[source,nginx]
----
server {
    listen 443 ssl;
    server_name ${SERVER_NAME};

    location /api/ {
        proxy_pass http://${BACKEND_HOST}:${BACKEND_PORT};
    }
}
----

官方 Nginx Container 常見：

[source,text]
----
/etc/nginx/templates/site.conf.template
        ↓ entrypoint / envsubst
/etc/nginx/conf.d/site.conf
        ↓ include
Nginx
----

[plantuml,nginx-template-flow,svg]
----
@startuml
left to right direction

rectangle Env as "Environment Variables"
rectangle Template as "site.conf.template"
rectangle Entry as "Entrypoint / envsubst"
rectangle Conf as "site.conf"
rectangle Nginx

Env --> Entry
Template --> Entry
Entry --> Conf : 產生
Conf --> Nginx : include / 載入
@enduml
----

重點：

* Template：先「產生」設定檔。
* Include：Nginx 再「載入」設定檔。
* `.template` 通常不是 Nginx 最終直接解析的檔案。

== HTTPS 與 TLS Termination

[source,nginx]
----
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/private.key;
    ssl_protocols TLSv1.2 TLSv1.3;
}

server {
    listen 80;
    server_name example.com;
    return 301 https://$host$request_uri;
}
----

[plantuml,nginx-tls-termination-flow,svg]
----
@startuml
left to right direction

actor User as "瀏覽器"
rectangle Nginx as "Nginx\nTLS / Certificate"
rectangle App as "Application\nSpring Boot / Tomcat"

User -> Nginx : HTTPS :443
Nginx -> App : HTTP :8080\n或內部 HTTPS
App --> Nginx : Response
Nginx --> User : HTTPS Response
@enduml
----

由 Nginx 統一處理 TLS 的作法稱為 TLS Termination。後端通常靠 `X-Forwarded-Proto` 得知原始連線是否為 HTTPS。

[NOTE]
====
Nginx 到後端是否能使用 HTTP，要依網路邊界與資安要求決定；跨主機、跨網段或零信任環境可能仍需內部 HTTPS。
====

=== Nginx 到底需要哪種憑證檔案？

Nginx 的 HTTPS 設定核心是：

[source,nginx]
----
ssl_certificate     /etc/nginx/ssl/fullchain.pem;
ssl_certificate_key /etc/nginx/ssl/server.key;
----

Nginx 官方的 +ssl_certificate+ 與 +ssl_certificate_key+ 主要讀取 **PEM 格式**。因此重點不是副檔名，而是檔案裡實際存放的格式。

[cols="18%,24%,28%,30%",options="header"]
|===
|副檔名 |通常包含 |Nginx 可否直接使用 |常見用途

|+.crt+
|網站憑證，可能是 PEM 或 DER
|PEM 可以；DER 需先轉換
|CA 核發的伺服器憑證

|+.cer+
|與 +.crt+ 類似，可能是 PEM 或 DER
|PEM 可以；DER 需先轉換
|Windows 或部分 CA 常見命名

|+.pem+
|可以放憑證、憑證鏈或私鑰
|可以
|Nginx 最常見的文字格式

|+.key+
|私鑰，通常是 PEM
|可以
|搭配 +ssl_certificate_key+

|+.p12+ / +.pfx+
|PKCS#12，可同時包含憑證、私鑰與憑證鏈，通常有密碼
|一般不直接給 Nginx 使用
|Tomcat、Spring Boot、IIS、Windows 常見

|+fullchain.pem+
|網站憑證 + 中繼憑證
|可以，通常最適合放在 +ssl_certificate+
|提供完整憑證鏈

|+chain.pem+
|中繼憑證
|不能單獨取代網站憑證
|與網站憑證合併成 fullchain
|===

[NOTE]
====
+.crt+、+.cer+、+.pem+ 不能只靠副檔名判斷格式。

PEM 通常可以直接看到：

[source,text]
----
-----BEGIN CERTIFICATE-----
...
-----END CERTIFICATE-----
----

如果是二進位 DER，就要先轉成 PEM。
====

=== 方案 A：已有 .crt + .key

如果 CA 已提供：

[source,text]
----
server.crt
server.key
----

而 +server.crt+ 本身就是 PEM，可以直接設定：

[source,nginx]
----
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/server.crt;
    ssl_certificate_key /etc/nginx/ssl/server.key;

    ssl_protocols TLSv1.2 TLSv1.3;
}
----

如果 CA 另外提供中繼憑證：

[source,text]
----
server.crt
intermediate.crt
server.key
----

建議依序合併成完整憑證鏈，**網站憑證放前面，中繼憑證放後面**：

[source,bash]
----
cat server.crt intermediate.crt > fullchain.pem
----

Nginx 改用：

[source,nginx]
----
ssl_certificate     /etc/nginx/ssl/fullchain.pem;
ssl_certificate_key /etc/nginx/ssl/server.key;
----

一般不需要把 Root CA 一起送給瀏覽器，重點是網站憑證與必要的中繼憑證鏈。

=== 方案 B：已有 fullchain.pem + .key

這是 Nginx 最單純的部署形式之一：

[source,text]
----
/etc/nginx/ssl/
├── fullchain.pem
└── server.key
----

[source,nginx]
----
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/server.key;

    ssl_protocols TLSv1.2 TLSv1.3;
}
----

=== 方案 C：Private Key 有密碼

Nginx 的私鑰不一定要是未加密狀態，也可以使用加密 PEM Private Key。

例如可能看到：

[source,text]
----
-----BEGIN ENCRYPTED PRIVATE KEY-----
...
-----END ENCRYPTED PRIVATE KEY-----
----

Nginx 可透過 +ssl_password_file+ 在啟動或 reload 時取得私鑰密碼：

[source,nginx]
----
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/server-encrypted.key;

    ssl_password_file /run/secrets/nginx_ssl_password;

    ssl_protocols TLSv1.2 TLSv1.3;
}
----

密碼檔每一行是一組可能的私鑰密碼，例如：

[source,text]
----
<private-key-passphrase>
----

[WARNING]
====
+ssl_password_file+ 本身就是敏感資料：

* 不可提交到 Git。
* 不可放進公開 Repository。
* 建議限制檔案權限。
* Container 環境可用 Docker / Podman Secret 掛載到 +/run/secrets/+。
====

例如：

[source,bash]
----
chmod 600 /etc/nginx/ssl/server-encrypted.key
chmod 600 /run/secrets/nginx_ssl_password
----

如果沒有要求私鑰一定要保留密碼，也常見把部署用私鑰轉成未加密 PEM，讓服務可以自動啟動；這種作法就必須更加嚴格限制私鑰檔案權限。

=== 方案 D：只有 .p12 / .pfx + 密碼

+.p12+ 與 +.pfx+ 都屬於 PKCS#12，常見會把下列內容打包在同一個檔案：

[source,text]
----
server.p12
├── Server Certificate
├── Private Key
└── Intermediate Certificate(s)
----

這種格式很適合 Tomcat、Spring Boot 或 IIS，但一般 Nginx **不能像 Tomcat / Spring Boot 一樣，直接指定 +.p12 / .pfx+ 再在設定檔填一組文字密碼**。

[WARNING]
====
這裡最容易混淆：

* Nginx 沒有一般用途的 +ssl_certificate_password 123456;+ 這類指令。
* +ssl_password_file+ **不是拿來解鎖 +.p12 / .pfx+ 的密碼**。
* +ssl_password_file+ 是提供「已經拆成 PEM 後，加密 Private Key 的 passphrase」。
* 所以 +.p12 / .pfx+ 通常要先用 OpenSSL 拆成 PEM Certificate / Chain / Private Key，再交給 Nginx。

也就是：

[source,text]
----
Tomcat / Spring Boot
.p12 / .pfx + password
        ↓
   可直接載入

Nginx
.p12 / .pfx + password
        ↓ OpenSSL
fullchain.pem + private.key
        ↓
      Nginx

只有 private.key 本身有密碼時
        ↓
ssl_password_file
----
====

下面這種寫法不是一般 Nginx 的 PKCS#12 使用方式：

[source,nginx]
----
# 錯誤觀念：把 .p12 同時當成憑證與私鑰
ssl_certificate     /etc/nginx/ssl/server.p12;
ssl_certificate_key /etc/nginx/ssl/server.p12;

# Nginx 也沒有這種標準指令
# ssl_certificate_password 123456;
----

正確做法通常是先使用 OpenSSL 拆成 PEM。

==== 取出伺服器憑證

[source,bash]
----
openssl pkcs12   -in server.p12   -clcerts   -nokeys   -out server.crt
----

執行時會要求輸入 PKCS#12 的匯入密碼。

==== 取出中繼憑證

[source,bash]
----
openssl pkcs12   -in server.p12   -cacerts   -nokeys   -out chain.crt
----

不同 PKCS#12 檔案不一定都內含獨立的中繼憑證，要以實際內容為準。

==== 取出未加密私鑰

[source,bash]
----
openssl pkcs12   -in server.p12   -nocerts   -nodes   -out server.key
----

[WARNING]
====
+-nodes+ 代表輸出的 Private Key 不再加密。

產出後應立即限制檔案權限：

[source,bash]
----
chmod 600 server.key
----
====

最後合併：

[source,bash]
----
cat server.crt chain.crt > fullchain.pem
----

Nginx 使用：

[source,nginx]
----
ssl_certificate     /etc/nginx/ssl/fullchain.pem;
ssl_certificate_key /etc/nginx/ssl/server.key;
----

=== 方案 E：從 .p12 拆出來，但 Private Key 仍保留密碼

如果希望拆出來後的私鑰仍保持加密，不加 +-nodes+：

[source,bash]
----
openssl pkcs12   -in server.p12   -nocerts   -out server-encrypted.key
----

OpenSSL 會要求：

. PKCS#12 的匯入密碼。
. 新輸出的 PEM Private Key passphrase。

Nginx 再搭配：

[source,nginx]
----
ssl_certificate     /etc/nginx/ssl/fullchain.pem;
ssl_certificate_key /etc/nginx/ssl/server-encrypted.key;
ssl_password_file   /run/secrets/nginx_ssl_password;
----

流程可以理解為：

[plantuml,nginx-pkcs12-to-pem-flow,svg]
----
@startuml
left to right direction

rectangle P12 as ".p12 / .pfx\nCert + Key + Chain"
rectangle OpenSSL
rectangle Cert as "fullchain.pem"
rectangle Key as "server.key\n或 encrypted.key"
rectangle Password as "password file\n加密 Key 才需要"
rectangle Nginx

P12 --> OpenSSL : PKCS#12 password
OpenSSL --> Cert
OpenSSL --> Key
Cert --> Nginx : ssl_certificate
Key --> Nginx : ssl_certificate_key
Password --> Nginx : ssl_password_file
@enduml
----

=== 方案 F：拿到的是 DER .cer / .crt

如果憑證是二進位 DER，可先轉成 PEM：

[source,bash]
----
openssl x509   -inform DER   -in server.cer   -out server.crt
----

再確認：

[source,bash]
----
openssl x509 -in server.crt -text -noout
----

之後依前面的 +.crt + .key+ 方式部署。

=== 如何確認憑證與 Private Key 是同一組

憑證與私鑰配錯時，Nginx 會無法正常載入 HTTPS。

可以分別取出 Public Key 再算 SHA-256：

[source,bash]
----
openssl x509   -in server.crt   -pubkey   -noout | openssl pkey -pubin -outform DER | openssl sha256
----

[source,bash]
----
openssl pkey   -in server.key   -pubout   -outform DER | openssl sha256
----

兩邊的 SHA-256 應相同。

如果 Private Key 本身有密碼，第二個指令會要求輸入 passphrase。

=== 檢查憑證內容、期限與憑證鏈

查看憑證：

[source,bash]
----
openssl x509   -in server.crt   -noout   -subject   -issuer   -dates
----

檢查 Nginx：

[source,bash]
----
nginx -t
----

從外部確認網站實際送出的憑證鏈：

[source,bash]
----
openssl s_client   -connect example.com:443   -servername example.com   -showcerts
----

也可以：

[source,bash]
----
curl -Iv https://example.com/
----

=== 完整 HTTPS Reverse Proxy 範例

[source,nginx]
----
server {
    listen 443 ssl;
    server_name example.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/server.key;

    ssl_protocols TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://127.0.0.1:8080;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

server {
    listen 80;
    server_name example.com;

    return 301 https://$host$request_uri;
}
----

=== 實務上怎麼選

[cols="32%,28%,40%",options="header"]
|===
|手上的檔案 |建議作法 |Nginx 最終設定

|+fullchain.pem+ + +server.key+
|直接使用
|+ssl_certificate+ + +ssl_certificate_key+

|+server.crt+ + +chain.crt+ + +server.key+
|先合併 fullchain
|+fullchain.pem+ + +server.key+

|+server.crt+ + 加密 +server.key+
|保留私鑰密碼
|再加 +ssl_password_file+

|+.p12+ / +.pfx+ + 密碼
|用 OpenSSL 拆成 PEM
|+fullchain.pem+ + +server.key+

|DER +.cer+ / +.crt+
|先轉成 PEM
|再依 +.crt + .key+ 部署
|===

一句話記法：

[source,text]
----
Tomcat / Spring Boot
  常直接使用 .p12 / .pfx + password

Nginx
  主要使用 PEM Certificate + PEM Private Key
  .p12 / .pfx 通常先用 OpenSSL 拆出來
----

更多憑證格式、CSR 與憑證鏈觀念可參考 xref:security/digital-certificates-guide.adoc[數位憑證與 Web Server 部署指南]。

== 負載平衡

[source,nginx]
----
upstream backend_servers {
    least_conn;
    server 10.0.0.11:8080;
    server 10.0.0.12:8080;
    keepalive 32;
}

location /api/ {
    proxy_pass http://backend_servers;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
}
----

[plantuml,nginx-load-balancing-flow,svg]
----
@startuml
left to right direction

actor User
rectangle Nginx
rectangle A as "Backend A\n10.0.0.11:8080"
rectangle B as "Backend B\n10.0.0.12:8080"

User -> Nginx : Request
Nginx --> A : Request 1
Nginx --> B : Request 2
A --> Nginx : Response
B --> Nginx : Response
Nginx --> User : Response
@enduml
----

`upstream` 定義後端群組，`proxy_pass http://backend_servers;` 則把請求交給這組服務。

=== WebSocket

map $http_upgrade $connection_upgrade {

location /events/ {

    proxy_cache off;
}
----

=== Timeout 與上傳

[source,nginx]
----
location /api/ {
    proxy_pass http://127.0.0.1:8080;

    proxy_send_timeout 60s;
    proxy_read_timeout 60s;
}

client_max_body_size 100m;

== 安全 Header、CORS 與存取控制

=== 常見安全 Header

[source,nginx]
----
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "geolocation=(), microphone=(), camera=()" always;
----

若要啟用 HSTS：

[source,nginx]
----
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
----

[WARNING]
====
啟用 `includeSubDomains` 前，必須確認所有子網域皆支援 HTTPS。
====

=== CORS

CORS 建議由單一層負責，避免後端與 Nginx 重複加入 Header。

[source,nginx]
----
location /api/ {
    add_header Access-Control-Allow-Origin "https://frontend.example.com" always;
    proxy_pass http://127.0.0.1:8080;
}
----

若使用 Cookie 或認證資訊，`Access-Control-Allow-Origin` 不可設為 `*`。

=== IP 白名單

[source,nginx]
----
location /admin/ {
    allow 192.168.1.0/24;
    deny all;
}
----

=== Basic Authentication

[source,nginx]
----
location /private/ {
    auth_basic "Restricted";
    auth_basic_user_file /etc/nginx/.htpasswd;
}
----

Basic Auth 應搭配 HTTPS。

== 自訂錯誤頁與 `proxy_intercept_errors`

最常見的做法是由 Nginx 統一顯示 404、502、503、504 等錯誤頁。

[source,nginx]
----
error_page 404 /404.html;
error_page 502 503 504 /500.html;

location /api/ {
    proxy_pass http://127.0.0.1:8080;
    proxy_intercept_errors on;
}

location = /404.html {
    root /usr/share/nginx/html;
    internal;
}

location = /500.html {
    root /usr/share/nginx/html;
    internal;
}
----

`error_page` 定義「哪些狀態要怎麼處理」，`proxy_intercept_errors on` 則決定是否攔截 upstream 的錯誤回應套用這些規則。

[plantuml,nginx-error-flow,svg]
----
@startuml
actor "瀏覽器" as Browser
participant "Nginx" as Nginx
participant "Upstream" as Upstream

Browser -> Nginx : Request
Nginx -> Upstream : Proxy Request
Upstream --> Nginx : HTTP status / Response

alt 符合 error_page 且 proxy_intercept_errors on
    Nginx -> Nginx : 套用自訂錯誤頁
    Nginx --> Browser : 自訂錯誤頁
else 其他情況
    Nginx --> Browser : upstream 原始回應
end
@enduml
----

公開錯誤頁不要顯示 Stack Trace、SQL、內部 IP、Framework 版本、實體路徑或內部專案名稱。

== Log 與問題排查

=== 建議 Log 格式

[source,nginx]
----
log_format main '$remote_addr - $remote_user [$time_local] '
                '"$request" $status $body_bytes_sent '
                'request_time=$request_time '
                'upstream_time=$upstream_response_time';

access_log /var/log/nginx/access.log main;
error_log /var/log/nginx/error.log warn;
----

重要欄位：

* `$status`：HTTP 狀態碼。
* `$request_time`：Nginx 處理整個請求的時間。
* `$upstream_response_time`：等待後端回應的時間。

=== 常見狀態碼

[cols="18%,32%,50%",options="header"]
|===
|狀態碼 |常見原因 |排查方向

|403
|權限、deny、SELinux
|檢查檔案權限與存取規則。

|404
|location、root、alias、URI 錯誤
|確認 Request 路徑與實體路徑。

|413
|Request Body 過大
|檢查 `client_max_body_size` 與後端限制。

|499
|用戶端提前中斷
|檢查前端 timeout、網路與後端處理時間。

|502
|無法連後端或 upstream 異常
|檢查程序、IP、port、防火牆與 Log。

|504
|後端回應逾時
|檢查後端效能與 `proxy_read_timeout`。
|===

=== 用 `curl` 驗證

[source,bash]
----
# 看 Header 與 Redirect
curl -I https://example.com/application-test/

# 看完整 Response
curl -i https://example.com/api/users

# 確認重新導向
curl -IL https://example.com/application-test/
----

若是 Context Path、Cookie 或 Redirect 問題，應同時檢查：

* Request URL。
* Response `Location`。
* Response `Set-Cookie` 的 `Path`。
* 後端實際收到的 URI。

== 公開 Repository 的安全檢查

公開 Nginx 文件或設定範例應移除：

* 真實公網或私網 IP。
* 實際網域與內部 DNS。
* 專案代碼與系統名稱。
* Container / VM / Pod 真實名稱。
* Cookie 真實名稱。
* 憑證組織資訊。
* 帳號、密碼、Token、Basic Auth 內容。
* Log 中的使用者識別資料。

推薦以 `example.com`、`127.0.0.1`、`10.0.0.x`、`application`、`backend-a` 等通用名稱取代。

== 正式環境檢查清單

* `nginx -t` 驗證成功。
* `nginx -T` 確認 include 展開結果。
* DNS、防火牆、後端 port 正確。
* HTTPS 憑證與完整憑證鏈正確。
* Proxy Header 正確。
* Context Path、Cookie Path、Redirect 已實際測試。
* Timeout 與上傳限制符合需求。
* Log 有輪替與容量管理。
* CORS、HSTS、安全 Header 經過測試。
* 錯誤頁不洩漏內部資訊。
* 設定有備份與 rollback 方法。
