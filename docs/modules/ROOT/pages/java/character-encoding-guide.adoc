== 說明

本文件整理字元、字集、編碼與 Java / Web / 資料庫 / PDF 之間的關係。

常見亂碼問題通常不是「中文不能顯示」，而是某個邊界把同一批 byte 用錯編碼解讀。只要 bytes 在進入 Java `String` 前已經被解錯，後續即使網頁是 UTF-8、PDF 字型正確，也可能無法還原原本內容。

適用情境：

* Java Web 專案處理 Big5、MS950、UTF-8、ISO-8859-1、UTF-16。
* 舊系統 URL 參數、Servlet、JSP、資料庫與 PDF 報表混用不同編碼。
* 資料庫查出來看似 ISO-8859-1，但需轉回 Big5 / MS950 才是正確中文字。
* PDFSERVLET、iText、JasperReports 或舊 Java 5 系統處理自造字、罕用字。

== 核心結論

字元處理要分清楚三件事：

[cols="22%,28%,50%", options="header"]
|===
|概念 |例子 |說明

|字元 Character
|`A`、`：`、`測`、`𠀀`
|人看到的文字單位。不同系統內部可能用不同方式表示。

|碼位 Code Point
|`U+0041`、`U+FF1A`、`U+6E2C`
|Unicode 為每個字元指定的編號。碼位本身還不是檔案或網路上實際傳輸的 bytes。

|編碼 Encoding / Charset
|UTF-8、UTF-16、Big5、MS950
|把碼位或字元轉成 bytes 的規則，也負責從 bytes 還原成字元。
|===

最重要的實務判斷：

* Java `String` 內部不是 Big5，也不是 UTF-8；Java `String` 是 Unicode 字串，實作上以 UTF-16 code unit 表示。
* Big5 / MS950 / UTF-8 是「資料進出 Java String 邊界時」使用的 byte 編碼。
* 網頁是 UTF-8，不代表資料庫或檔案也是 UTF-8。
* 資料庫是 Big5 / MS950，不代表 Java 程式內的字串仍是 Big5。
* 只要來源 bytes 先正確解碼成 Java `String`，後續輸出成 UTF-8 網頁通常不會亂碼。

== Java String 與外部編碼

Java `String` 是中間橋樑。

[source,text]
----
外部 bytes
  -> 依來源編碼解碼
  -> Java String
  -> 依輸出編碼重新編碼
  -> 外部 bytes
----

例如資料來源是 Big5 / MS950，網頁輸出是 UTF-8：

[source,text]
----
資料庫 Big5/MS950 bytes
  -> JDBC 或程式用 Big5/MS950 解碼
  -> Java String
  -> Servlet / Spring 用 UTF-8 輸出
  -> 瀏覽器用 UTF-8 解讀
  -> 顯示正確中文
----

不會亂碼的原因是：Big5 bytes 已經先變成正確 Java `String`，網頁輸出時再由 Java `String` 正確編成 UTF-8 bytes。

會亂碼的常見原因是：Big5 bytes 尚未正確解碼，就被當成 UTF-8 或其他編碼處理。

== 每種編碼的容量概念

不同編碼使用不同 byte 數表示一個字元。

[cols="18%,18%,28%,36%", options="header"]
|===
|編碼 |每個字元常見大小 |適合範圍 |說明

|ASCII
|1 byte
|英文字母、數字、基本符號
|只定義 `0x00` 至 `0x7F`。UTF-8 與多數舊編碼都保留 ASCII 相容區。

|ISO-8859-1
|1 byte
|西歐文字、byte 容器
|`0x00` 至 `0xFF` 每個 byte 都能一對一映射成字元。實務上常被拿來暫存原始 bytes，但不是中文編碼。

|Big5
|ASCII 1 byte；中文多為 2 bytes
|繁體中文舊系統
|英數字通常仍是 ASCII 1 byte，中文字與全形符號多為 2 bytes。

|MS950 / CP950
|ASCII 1 byte；中文多為 2 bytes
|Windows 繁中、台灣舊系統
|可視為 Big5 的 Windows 擴充版本，涵蓋更多符號與常見擴充字。

|UTF-8
|1 至 4 bytes
|Web、JSON、現代系統
|ASCII 仍是 1 byte；常用中文通常 3 bytes；補充平面字元通常 4 bytes。

|UTF-16
|2 或 4 bytes
|Java String、Windows API 內部常見
|BMP 內字元通常 2 bytes；超出 BMP 的字元用 surrogate pair，合計 4 bytes。

|UTF-32
|4 bytes
|少數內部處理或研究用途
|每個碼位固定 4 bytes，空間成本高，Web 與 Java 一般不使用。
|===

注意：這裡的「每個字元」是實務簡化說法。Unicode 有組合字、emoji 序列、variation selector 等情境，一個使用者看到的「一個字」不一定等於一個 code point。

== Big5 與 MS950

Big5 是繁體中文舊系統常見編碼。MS950 又稱 CP950，是 Microsoft Windows 繁中環境常用的 Big5 擴充。

實務上常見差異：

[cols="20%,80%", options="header"]
|===
|項目 |說明

|Big5
|傳統繁中文字集，常見於早期台灣系統、資料庫、文字檔與報表。

|MS950 / CP950
|Windows 繁中 code page，與 Big5 大致相容，但包含一些擴充對應。Java 舊系統處理台灣繁中資料時，常比單純 `Big5` 更符合實際資料。

|自造字 / 罕用字
|常落在 Big5 使用者自訂區或廠商擴充區，例如 `FA40`、`8140`、`8E40` 類碼位。是否能正確顯示，取決於解碼、字型、造字表與報表工具是否一致。
|===

若來源 byte 是台灣舊系統資料，優先確認應使用 `Big5` 還是 `MS950`。不要只因為系統顯示「Big5」就假設 Java 的 `Big5` charset 一定完全符合。

== Big5 報表遇到非 Big5 字元

Big5 報表或 Big5 文字檔只能直接表示 Big5 / MS950 可編碼的字元。若 Java `String` 內含非 Big5 區間的字元，例如部分 Unicode 罕用字、emoji、特殊符號、私用區字元或系統未定義的造字碼，輸出到 Big5 報表時就會遇到「目的編碼無法表示」的問題。

常見處理方式如下：

[cols="24%,36%,40%", options="header"]
|===
|處理方式 |呈現結果 |說明

|直接以 Big5 / MS950 編碼
|`?` 或替代字元
|編碼器找不到對應 byte 時，常會以問號或替代字元輸出。此時原字通常已不可逆。

|轉成 HTML entity
|`&#12345;`、`&#x3039;`
|將字元改寫成 ASCII 文字組合。因為 `&`、`#`、數字、`;` 都在 ASCII / Big5 可表示範圍內，所以 Big5 報表可保存這串文字。

|使用造字或圖片流程
|顯示自造字圖形
|報表工具需支援造字碼表、字型或圖片替換流程。這通常是舊式地政、戶政或公部門系統才會有的客製能力。
|===

`&#12345;` 是 HTML numeric character reference，不是 Big5 編碼。它的意義是「以十進位 Unicode code point 表示某個字元」。例如：

[source,text]
----
&#12345;   十進位 HTML entity
&#x3039;  十六進位 HTML entity
----

這種做法的好處是資料可以安全穿過 Big5 文字報表或舊式 byte 流，因為它只使用 ASCII 字元。限制是：報表工具若只是把文字畫到 PDF 上，使用者看到的會是 `&#12345;` 這串字，而不是原本字元；只有在後續流程有做 HTML entity decode，才會還原成真正的 Unicode 字元。

因此 Big5 報表看到 `&#12345;` 類內容時，判斷重點是：

* 如果報表規格要求保留原字語意，這通常是「無法直接以 Big5 表示，所以暫存為 entity」。
* 如果報表最後應顯示真正字元，就必須確認哪一層負責 HTML entity decode，以及 decode 後的 PDF 字型是否能顯示該字。
* 如果報表本來就是純文字或固定欄寬格式，不一定適合自動 decode，因為 decode 後的字寬可能改變排版。
* `&#12345;` 只保留 Unicode 碼位，不能保證保留原始 Big5 造字 byte；若原系統依 `FA40`、`8140` 這類碼位找造字圖，仍需保存原始碼位或額外對照表。

== UTF-8 與 UTF-16

UTF-8 是 Web 最常見的傳輸與檔案編碼。

UTF-8 特性：

* ASCII 字元仍是 1 byte，例如 `A` 是 `41`。
* 常用中文通常是 3 bytes，例如 `測` 是 `E6 B8 AC`。
* 超出基本多文種平面（BMP）的字元通常是 4 bytes。
* 適合 HTML、JSON、YAML、Markdown、AsciiDoc、REST API。

UTF-16 是 Java `String` 內部表示的基礎。

UTF-16 特性：

* BMP 內字元通常用 2 bytes / 1 個 code unit 表示，例如 `測` 是 `U+6E2C`。
* 超出 BMP 的字元用 surrogate pair，Java `String.length()` 會算成 2 個 `char`。
* Java 的 `char` 是 16-bit code unit，不一定等於一個完整 Unicode 字元。

常見誤解：

[source,java]
----
new String(bytes, "Unicode")
----

這不是「把資料轉成 Unicode」的通用做法。第二個參數代表「用哪個 charset 解讀這批 bytes」。若 `bytes` 是 Big5 / MS950，就應使用來源編碼：

[source,java]
----
new String(bytes, "Big5")
new String(bytes, "MS950")
----

`Unicode` 在 Java 中通常是 UTF-16 類型的別名或相關實作，拿來解 Big5 bytes 會亂掉。

== ISO-8859-1 作為 byte 容器

ISO-8859-1 每個 byte `0x00` 至 `0xFF` 都可一對一對應成同碼位字元。舊系統常利用這點，把「其實是 Big5 的 bytes」暫時放進 Java `String`。

常見修正方式：

[source,java]
----
String wrong = resultFromDb;
String fixed = new String(wrong.getBytes("ISO-8859-1"), "MS950");
----

這段的意思不是「ISO-8859-1 轉 Big5 文字」，而是：

[source,text]
----
wrong 這個 String 只是暫存原始 bytes
  -> 用 ISO-8859-1 取回原本每個 byte
  -> 用 MS950 正確解讀 bytes
  -> 得到正確 Java String
----

這種做法只適合確認資料真的被 ISO-8859-1 當 byte 容器誤讀的情境。若資料已經被錯誤解碼成 `?` 或 `U+FFFD`，原始 byte 已不可逆，通常無法靠這段救回。

== URL percent-encoding 與 HTML entity

URL、HTML 與 charset 是不同層次的問題，常被混在一起討論。

URL 不能安全直接放所有 Unicode 字元。瀏覽器或程式通常會把 URL path、query string 中的非 ASCII 字元轉成 percent-encoding，也就是每個原始 byte 以 `%HH` 表示。若 URL 使用 UTF-8，中文字會先轉成 UTF-8 bytes，再逐 byte 改成 `%HH`。

例如：

[source,text]
----
原始 URL：
https://example.com/docs/中文資料夾/測試文件-01大綱.html

percent-encoding 後：
https://example.com/docs/%E4%B8%AD%E6%96%87%E8%B3%87%E6%96%99%E5%A4%BE/%E6%B8%AC%E8%A9%A6%E6%96%87%E4%BB%B6-01%E5%A4%A7%E7%B6%B1.html
----

其中 `中` 的 UTF-8 bytes 是 `E4 B8 AD`，所以在 URL 中會變成 `%E4%B8%AD`。

HTML entity 則是 HTML 內容層的表示方式，例如：

[source,html]
----
&#39640;      <!-- 高，十進位 Unicode code point -->
&#x9AD8;     <!-- 高，十六進位 Unicode code point -->
&amp;       <!-- & -->
&lt;        <!-- < -->
&gt;        <!-- > -->
&quot;      <!-- " -->
----

兩者差異如下：

[cols="22%,30%,48%", options="header"]
|===
|類型 |例子 |用途

|URL percent-encoding
|`%E9%AB%98`
|用在 URL path、query string、form URL encoded 等位置，表示原始 bytes。

|HTML numeric entity
|`&#39640;`、`&#x9AD8;`
|用在 HTML 內容或屬性值中，表示 Unicode 字元。

|HTML named entity
|`&amp;`、`&lt;`
|用在 HTML 內容或屬性值中，避免特殊符號被當成 HTML 語法。
|===

實務注意事項：

* URL percent-encoding 的 `%E9%AB%98` 代表 UTF-8 bytes，不是 Big5，也不是 HTML entity。
* HTML 內容中的 `&#39640;` 代表 Unicode 碼位，不代表 UTF-8 bytes。
* 若在 HTML 中輸出 URL，通常會同時遇到兩層：URL 本身需要 percent-encoding，而 HTML 屬性中的 `&` 需要寫成 `&amp;`。
* Java Web 接收 query string 時，要確認 Servlet container 使用哪個 URI encoding；舊 Tomcat 常需要設定 `URIEncoding="UTF-8"`。
* 不要對同一段內容重複 encode 或重複 decode，否則可能出現 `%25E9%25AB%2598` 這類二次編碼結果。

== 網頁、資料庫與報表的編碼邊界

企業系統常見資料流如下：

[source,text]
----
資料庫 bytes
  -> JDBC driver / 程式解碼
  -> Java String
  -> Controller / Template / JSON
  -> HTTP response charset，例如 UTF-8
  -> 瀏覽器顯示
----

報表流程如下：

[source,text]
----
資料庫 bytes
  -> Java String
  -> 報表引擎 / PDF 工具
  -> 字型與 PDF 內部編碼
  -> PDF Reader 顯示
----

因此每個邊界都要分開確認：

[cols="24%,28%,48%", options="header"]
|===
|邊界 |常見設定 |注意事項

|資料庫到 Java
|DB charset、JDBC driver、TypeHandler
|查出來若是亂碼，要先判斷 JDBC 是否已解碼錯誤。

|Java 到網頁
|`Content-Type: text/html; charset=UTF-8`、JSON UTF-8
|Java `String` 正確時，輸出 UTF-8 通常可正確顯示。

|HTTP request 到 Java
|`request.setCharacterEncoding(...)`、Connector `URIEncoding`
|POST body、query string、form submit 的處理點不同。

|Java 到 PDF
|iText BaseFont、Jasper 字型、Identity-H、Big5 字型
|PDF 能否顯示取決於字型是否有 glyph，以及 PDF 工具如何編碼文字。

|檔案到 Java
|`Files.readString(path, charset)`、`InputStreamReader`
|讀 Big5 檔案不可用平台預設編碼猜測。
|===

== PDFSERVLET 自造字案例

舊式 PDFSERVLET 常見傳參方式是把文字轉成 HEX 放到 URL：

[source,text]
----
user_name=B4FAB8D5FA4081408E40
----

其中：

[cols="24%,76%", options="header"]
|===
|片段 |說明

|`B4FA B8D5`
|一般 Big5 / MS950 中文，代表「測試」。

|`FA40 8140 8E40`
|造字或擴充字碼位，需由接收端依 MS950 與造字流程處理。
|===

錯誤寫法：

[source,java]
----
new String(HexUtil.toByteArray(hexValue))
----

此寫法依 JVM 預設編碼解讀，若預設 `Big5` 無法正確處理擴充碼位，進入 Java `String` 前就會壞掉。

修正寫法：

[source,java]
----
new String(HexUtil.toByteArray(hexValue), "MS950")
----

修正後才能讓 Java `String` 保留對應的 Unicode 私用區或擴充字碼位，後續造字圖片流程才有機會正確處理。

== Big5 自造字區間、MS950 與 Unicode 對應

Big5 自造字不是 Unicode 已統一定義的標準字元。Big5 byte、Unicode 碼位及字型 glyph 必須使用同一版對照，否則同一個碼值可能顯示成不同字，或完全無法顯示。

本章所稱「Big5 自造字區」需區分下列兩種範圍：

* 全字庫所列 Big5 使用者造字區共有 3 段、5,809 碼。
* Windows code page 950 的 EUDC 範圍另包含 `C6A1-C8FE`，共有 4 段、6,217 碼。

兩者不可只以「Big5」概括。Big5-1984、Big5-ETen、Big5-2003、Microsoft CP950、Java `Big5` 與 Java `MS950` 對擴充區的處理可能不同。

=== Big5 雙位元碼的排列方式

Big5 中文及全形字元通常使用 2 bytes：

* 第一個 byte 為 lead byte，常見範圍是 `81-FE`。
* 第二個 byte 為 trail byte，可使用 `40-7E` 或 `A1-FE`。
* `7F` 及 `80-A0` 不在一般 Big5 trail byte 範圍內。
* 一個完整 lead byte 可排列 `63 + 94 = 157` 個雙位元碼。

因此 `FA40-FEFE` 並不是把 `FA40` 到 `FEFE` 的所有十六進位值都算進去；每一列都要跳過無效的 trail byte。

=== Windows CP950 EUDC 與 Java MS950 對應

Microsoft 對 code page 950 宣告的 EUDC 範圍是 `8140-8DFE`、`8E40-A0FE`、`C6A1-C8FE`、`FA40-FEFE`。其中 `C6A1-C8FE` 有 408 碼，因此 Windows EUDC 範圍合計 6,217 碼。

Java `MS950` 會把這 4 段依下列順序映射到 Unicode 基本多文種平面（BMP）的私用區。UTF-8 欄位是該 Unicode 區間兩端編碼後的 bytes，不是另一份造字對照表。

[cols="18%,12%,20%,25%,25%", options="header"]
|===
|Big5 / MS950 bytes |碼數 |Java `MS950` 解碼結果 |UTF-8 起點 |UTF-8 終點

|`FA40-FEFE`
|785
|`U+E000-U+E310`
|`EE 80 80`
|`EE 8C 90`

|`8E40-A0FE`
|2,983
|`U+E311-U+EEB7`
|`EE 8C 91`
|`EE BA B7`

|`8140-8DFE`
|2,041
|`U+EEB8-U+F6B0`
|`EE BA B8`
|`EF 9A B0`

|`C6A1-C8FE`
|408
|`U+F6B1-U+F848`
|`EF 9A B1`
|`EF A1 88`

|合計
|6,217
|`U+E000-U+F848`
|`EE 80 80`
|`EF A1 88`
|===

參考：link:https://learn.microsoft.com/en-us/windows/win32/intl/eudccoderange[Microsoft EUDCCodeRange]。上表的 Unicode 對應亦可由 Java `MS950` charset 驗證。

典型轉換如下：

[source,text]
----
MS950 bytes FA 40
  -> Java MS950 decode
  -> Unicode U+E000
  -> UTF-8 bytes EE 80 80

MS950 bytes 81 40
  -> Java MS950 decode
  -> Unicode U+EEB8
  -> UTF-8 bytes EE BA B8
----

Unicode BMP 私用區的完整範圍是 `U+E000-U+F8FF`，共有 6,400 個碼位；Java `MS950` 上述映射使用到 `U+F848`，尚有 `U+F849-U+F8FF` 共 183 個碼位未由這 4 段 MS950 bytes 對應。私用區只保留碼位，不規定字義及字形；`U+E000` 在不同機關、專案或字型中可能代表完全不同的字。

參考：link:https://www.unicode.org/faq/private_use.html[Unicode 私用字元說明]。

=== `C6A1-C8FE` 的相容性風險

`C6A1-C8FE` 是最需要特別確認的區段。它在不同 Big5 衍生版本中可能是符號、日文假名、保留區或 EUDC，不能只看 bytes 就判斷字義。

例如在 Java 中：

[cols="22%,30%,48%", options="header"]
|===
|bytes |charset |解碼結果

|`C6 A1`
|`Big5`
|`U+30FE`，日文片假名重複記號。

|`C6 A1`
|`MS950`
|`U+F6B1`，Unicode 私用區碼位。
|===

所以自造字資料不可在 `Big5`、`MS950`、Big5-HKSCS 或瀏覽器的 `big5` 解碼器之間任意替換。正式轉換前至少要保存並確認：

* 原始 Big5 / MS950 bytes。
* 使用的 charset 名稱與 Java / 作業系統版本。
* 造字對照表版本。
* 配套字型檔及其版本或雜湊值。

=== `kaiu.ttf` 與 `EUDC.TTE` 的差別

常見造字套件可能同時提供完整中文字型與獨立 EUDC 字型。獨立檔案的副檔名可能是 `.TTE`，其內容仍屬 TrueType 字型資料，但用途與完整的 `.ttf` 中文字型不同。

以下為整合造字版本常見的檔案差異；實際涵蓋範圍仍應以各檔案的 cmap 檢查結果為準：

[cols="18%,20%,22%,40%", options="header"]
|===
|檔案 |字型家族 |cmap 涵蓋範圍 |通常用途

|`kaiu.ttf`
|`DFKai-SB`／標楷體
|一般拉丁文、符號、常用中文字及 `U+E000-U+F848`
|完整楷體字型，可直接指定為畫面或 PDF 字型；整合造字版本可能已把 MS950 EUDC 對應的私用區 glyph 併入字型。

|`MingLiU.ttf`
|`MingLiU`／細明體
|一般拉丁文、符號、常用中文字及 `U+E000-U+F848`
|完整明體字型，結構與整合造字版 `kaiu.ttf` 類似，但字形風格不同。

|`EUDC.TTE`
|`EUDC`
|通常只涵蓋 Unicode 私用區，例如 `U+E000-U+F848` 或 `U+E000-U+F8FF`
|獨立的 EUDC 字型，通常由 Windows GDI 經登錄設定連結到目前字型；不是用來單獨顯示一般中英文的完整字型。
|===

部分 Windows 造字安裝程式會設定下列使用者登錄，將獨立 EUDC 字型設為 code page 950 的預設造字字型：

[source,text]
----
HKEY_CURRENT_USER\EUDC\950
  SystemDefaultEUDCFont=<EUDC 字型檔路徑>
----

Windows GDI 顯示私用區字元時，會先尋找目前字型的關聯 EUDC 字型，找不到時再查 `SystemDefaultEUDCFont`。因此文字本身即使已是 `U+E000`，仍要有內容相符的 EUDC 字型才看得到正確字形。參考：link:https://learn.microsoft.com/en-us/windows/win32/intl/eudc[Microsoft EUDC 登錄設定]。

=== Windows、Java、Web 與 PDF 的顯示差異

[cols="20%,32%,48%", options="header"]
|===
|環境 |字型取得方式 |注意事項

|Windows 傳統 GDI 程式
|可使用 `HKEY_CURRENT_USER\EUDC\950` 的字型連結
|需確認非 Unicode 程式語言、code page 950、登錄值及 EUDC 檔案路徑一致。

|Java AWT / Swing
|Java 邏輯字型 fallback、作業系統字型或程式明確載入

=== 自造字轉 Unicode 的處理原則

私用區轉成 UTF-8，只是把私用區碼位改用 UTF-8 bytes 保存，並沒有把自造字變成 Unicode 標準字。

[source,text]
----
FA40 -> U+E000 -> EE 80 80
----

上例只能保證碼位可通過 UTF-8 系統傳輸。接收端若沒有同一套字型，`U+E000` 仍可能顯示空白、方框或另一個字。

若全字庫或 Unicode 已收錄該字，長期做法應建立經確認的「原始 MS950 bytes / PUA 碼位 / 正式 Unicode 碼位」對照，再逐字遷移。不可直接用碼位位移或字型外觀猜測正式 Unicode，因為：

* 同一個 PUA 碼位可由不同單位定義成不同字。
* 同一字可能已有 BMP、CJK Extension B 以上的補充平面碼位，或異體字序列。
* 補充平面字元在 Java `String` 中使用 surrogate pair，不能只用單一 `char` 處理。
* 轉成正式 Unicode 後，仍要確認網頁與 PDF 字型具有對應 glyph。

== 常見錯誤與正確寫法

[cols="36%,32%,32%", options="header"]
|===
|情境 |錯誤寫法 |建議寫法

|Big5 bytes 建立字串
|`new String(bytes)`
|`new String(bytes, "MS950")`

|Big5 bytes 當 UTF-8 讀取
|`new String(bytes, "UTF-8")`
|確認來源後使用 `Big5` 或 `MS950`

|以為 `Unicode` 可自動轉正
|`new String(bytes, "Unicode")`
|依來源 bytes 使用正確 charset

|讀 Big5 文字檔
|`Files.readString(path)`
|`Files.readString(path, Charset.forName("MS950"))`

|輸出 UTF-8 網頁
|未設定 charset
|`Content-Type: text/html; charset=UTF-8`

|資料庫 ISO-8859-1 容器轉正
|直接輸出 `wrong`
|`new String(wrong.getBytes("ISO8859-1"), "MS950")`

|Big5 報表遇到非 Big5 字元
|直接 Big5 編碼後變成 `?`
|依報表規格保留 entity，例如 `&#12345;`，或走造字 / 圖片替換流程

|URL 中文路徑
|直接拼接未編碼中文或重複編碼
|依 URL 規則做 percent-encoding，例如 `高` 以 UTF-8 表示為 `%E9%AB%98`
|===

== 排查流程

遇到亂碼時，不要先猜字型。建議依序確認：

. 原始資料來源是 bytes、Java `String`、資料庫欄位，還是 URL 參數。
. 原始 bytes 的真正編碼是 UTF-8、Big5、MS950、ISO-8859-1 還是其他。
. Java `String` 內目前是否已經出現 `?`、`U+FFFD` 或 `@`。
. 若已不可逆，需回到更前面的 byte 來源處理。
. 若 Java `String` 正確但畫面錯誤，再檢查 HTTP response charset。
. 若 Java `String` 正確但 PDF 錯誤，再檢查 PDF 字型與報表工具編碼。
. 若只有自造字錯誤，再檢查造字碼表、字型、私用區與舊系統對照表。

可用 Java 印出 byte 與 code point：

[source,java]
----
String s = "測試";

System.out.println(Integer.toHexString(s.charAt(0))); // 6e2c
System.out.println(Integer.toHexString(s.charAt(1))); // 8a66

byte[] ms950 = s.getBytes("MS950");
for (byte b : ms950) {
    System.out.printf("%02X ", b & 0xff);
}
// B4 FA B8 D5
----

== 實務建議

* 新系統檔案、HTML、JSON、API 優先使用 UTF-8。
* 舊系統資料進入 Java 前，先確認來源 byte 編碼，不要依平台預設值。
* 台灣繁中舊系統遇到 Big5 問題時，優先測試 `MS950`。
* `new String(bytes)` 與 `String.getBytes()` 不要在正式程式中省略 charset。
* 如果資料已變成 `?` 或 `U+FFFD`，通常代表原始 byte 已遺失，應回到前一層修正。
* PDF 顯示問題要分成「字串是否正確」與「字型是否有 glyph」兩階段排查。
* 自造字問題通常同時牽涉 byte 編碼、Unicode 私用區、字型與舊系統對照表，不應只換字型或只改網頁 charset。
* `&#12345;`、`%E9%AB%98`、`\u9AD8` 是不同層次的表示法；排查時先確認目前字串是在 HTML、URL、JSON、Java `String` 還是外部 bytes。
