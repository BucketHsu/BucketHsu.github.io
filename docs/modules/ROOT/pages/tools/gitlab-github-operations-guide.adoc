GitLab 與 GitHub 都以 Git repository、branch、commit 與 code review 為核心，但介面名稱、權限模型、審核機制及 CI/CD 設定位置不同。

本文件整理從 GitLab 轉換到 GitHub 時最常遇到的名詞差異，並提供 GitHub repository 建立後的基礎設定清單。

NOTE: GitHub 與 GitLab 的部分功能會依 Free、Team、Enterprise、GitLab tier、公開或私人 repository 而不同。實際可用項目仍應以目前方案與管理介面為準。

== 核心觀念

GitLab 的 Merge Request 與 GitHub 的 Pull Request，本質上都是：

[source,text]
----
來源 branch
  ↓ 提出變更、審查、CI 驗證
目標 branch
  ↓ 合併
main
----

兩者只是命名不同：

* GitLab 強調「請求將 branch merge 進目標 branch」，因此稱為 Merge Request，簡稱 MR。
* GitHub 沿用「請求維護者 pull 你的變更」的概念，因此稱為 Pull Request，簡稱 PR。

實務上可直接記成：

[source,text]
----
GitLab MR ≒ GitHub PR
----

== Merge Request 與 Pull Request 的操作對照

=== 建立流程

GitLab 常見流程：

[source,text]
----
建立 feature branch
→ push 到 GitLab
→ Create merge request
→ 指定 target branch
→ 指定 Reviewer / Assignee
→ Pipeline 執行
→ Approve
→ Merge
----

GitHub 對應流程：

[source,text]
----
建立 feature branch
→ push 到 GitHub
→ Open pull request
→ 指定 base branch
→ 指定 Reviewer / Assignee
→ GitHub Actions / checks 執行
→ Approve
→ Merge pull request
----

GitHub PR 畫面中的 branch 名稱：

[cols="25%,35%,40%", options="header"]
|===
|名稱 |概念 |範例

|base
|要接收變更的目標 branch
|`main`

|compare / head
|提供變更的來源 branch
|`feature/login`
|===

也就是：

[source,text]
----
base: main ← compare: feature/login
----

=== Reviewer 與 Assignee

Reviewer 與 Assignee 不應混用。

Reviewer：

* 負責閱讀 diff。
* 留下 review comment。
* 執行 Approve、Comment 或 Request changes。
* 通常會影響是否允許合併。

Assignee：

* 表示誰負責處理或推進這個 PR。
* 可以是作者、協調者或負責修正的人。
* 單純指定 Assignee 通常不代表已完成 code review。

建議團隊規則：

[source,text]
----
Author     = 提交與修正變更
Reviewer   = 審查與核准變更
Assignee   = 負責讓 PR 持續往前推進
----

=== Approve 與 Request changes

GitHub Reviewer 可以選擇：

* Comment：只留下意見，不直接核准或阻擋。
* Approve：同意變更。
* Request changes：要求修改；若 branch rule 要求 review，通常會阻擋合併，直到問題被處理並重新核准。

只有在 Ruleset 或 Branch protection 中設定 required approving reviews，Approve 才會成為強制合併條件。

=== Draft PR

GitHub Draft Pull Request 對應 GitLab Draft Merge Request。

適合下列情境：

* 工作尚未完成，但希望提早讓其他人看到。
* 先讓 CI 執行。
* 需要討論設計或確認方向。
* 暫時不應合併。

完成後再切換為 Ready for review。

=== Merge 方式

GitHub 常見三種方式：

[cols="25%,35%,40%", options="header"]
|===
|方式 |結果 |適合情境

|Create a merge commit
|保留 feature branch 的所有 commit，並額外產生 merge commit
|需要保留完整 branch 合併歷史。

|Squash and merge
|把 PR 中多個 commit 合成一個 commit
|希望 `main` 歷史簡潔，功能以一個 commit 表示。

|Rebase and merge
|把來源 commit 依序接到目標 branch
|希望保持線性歷史，但仍保留每個 commit。
|===

小型團隊常用建議：

[source,text]
----
預設：Squash and merge
特殊需求：Create a merge commit
有嚴格 commit 整理規範時：Rebase and merge
----

IMPORTANT: 團隊應固定主要 merge 策略，否則 commit history 會同時混合 merge commit、squash commit 與 rebase commit，增加追查成本。

== GitLab CI 與 GitHub Actions 差異

=== 設定檔位置

GitLab：

[source,text]
----
.gitlab-ci.yml
----

GitHub：

[source,text]
----
.github/workflows/build.yml
.github/workflows/test.yml
.github/workflows/deploy.yml
----

GitHub 可以將不同目的拆成多個 workflow；每個 workflow 由 `on` 定義觸發條件。

=== Stage 與 needs

GitLab 常見寫法：

[source,yaml]
----
stages:
  - test
  - build
  - deploy
----

GitHub Actions 沒有完全相同的全域 stage 概念，通常透過 job 的 `needs` 建立順序：

[source,yaml]
----
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  build:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: npm run build

  deploy:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: ./deploy.sh
----

=== 觸發條件

GitLab 常見：

* `rules`
* `only` / `except`
* branch、tag、merge request、檔案變更條件

GitHub 常見：

* `push`
* `pull_request`
* `workflow_dispatch`
* `schedule`
* `paths` / `paths-ignore`
* branch、tag 條件

=== Variables 與 Secrets

一般非機密參數可放 Variables；密碼、token、private key 等敏感資料應放 Secrets。

GitHub 常見位置：

[source,text]
----
Repository
→ Settings
→ Secrets and variables
→ Actions
----

可再依環境放入 Environment secrets，例如 `staging` 與 `production`。

WARNING: Secret 不應寫進 workflow YAML、repository、log 或 Artifact。即使 GitHub 會遮罩部分 secret，也不代表可以主動輸出敏感值。

== GitHub 新 Repository 建立後應準備的檔案

=== 基本檔案

[cols="25%,35%,40%", options="header"]
|===
|項目 |用途 |建議

|`README.md` 或 `README.adoc`
|說明專案目的、建置、執行與部署方式
|幾乎所有 repository 都應建立。

|`.gitignore`
|排除編譯產物、IDE 設定、暫存檔與 secret
|依 Java、Node.js、Python 等技術選擇。

|`LICENSE`
|定義其他人可以如何使用程式碼
|公開 repository 應明確選擇；沒有 LICENSE 不代表自動開源。

|`CONTRIBUTING.md`
|說明 branch、commit、PR、測試與 review 規則
|多人協作時建議建立。

|`CODEOWNERS`
|指定特定路徑的預設 Reviewer
|重要模組或多人團隊建議建立。

|`SECURITY.md`
|說明安全漏洞回報方式與支援版本
|公開專案或正式產品建議建立。

|`CHANGELOG.md`
|記錄版本變更
|有 release 流程時建議建立。

|`.github/pull_request_template.md`
|統一 PR 說明格式
|要求作者填寫目的、測試與風險。

|`.github/ISSUE_TEMPLATE/`
|統一 Bug、Feature 等 Issue 格式
|公開專案或需求量較大時使用。

|`.github/workflows/`
|GitHub Actions workflow
|至少建立 build 或 test 驗證。
|===

=== CODEOWNERS 範例

[source,text]
----
# 預設所有檔案
* @team-maintainers

# 後端
/src/main/java/ @backend-team

# CI/CD
/.github/workflows/ @devops-team

# 安全設定
/security/ @security-team
----

CODEOWNERS 常見位置：

[source,text]
----
.github/CODEOWNERS
CODEOWNERS
docs/CODEOWNERS
----

要強制 Code Owner 核准，還需在 Ruleset 或 Branch protection 中啟用 require review from Code Owners。

=== Pull Request Template 範例

[source,markdown]
----
## 變更內容

## 變更原因

## 驗證方式

- [ ] 單元測試通過
- [ ] 整合測試通過
- [ ] 已確認無敏感資訊

## 風險與回復方式
----

== 保護 main 分支

GitHub 現在可使用 Repository Rulesets 或傳統 Branch protection rule。新設定通常可優先考慮 Rulesets，因為可以集中管理多個 branch、tag 與 bypass 權限；既有 repository 繼續使用 Branch protection 也可以。

=== 建議規則

對一般多人協作 repository，`main` 建議設定：

* Require a pull request before merging。
* Require approvals，至少 1 人。
* Dismiss stale pull request approvals when new commits are pushed。
* Require review from Code Owners，若有使用 `CODEOWNERS`。
* Require status checks to pass before merging。
* Require branches to be up to date before merging，視團隊流程決定。
* Require conversation resolution before merging。
* Block force pushes。
* Restrict deletions。
* 不允許一般開發者直接 push 到 `main`。
* 管理者是否允許 bypass，應依緊急修復流程決定。

=== 建議最小設定

個人或小型 repository：

[source,text]
----
Target branch: main
Require pull request: On
Required approvals: 1
Require status checks: On
Require conversation resolution: On
Block force push: On
Block deletion: On
----

團隊正式專案可再增加：

[source,text]
----
Dismiss stale approvals: On
Require Code Owner review: On
Require signed commits: 視政策
Require linear history: 視 merge 策略
Restrict who can push: 指定管理者或 release bot
Bypass list: 僅保留必要帳號
----

=== 為什麼不應直接 push main

直接 push 會略過：

* Reviewer 審查。
* PR 討論與歷史。
* required status checks。
* Code Owner approval。
* 合併前的衝突確認。
* 自動化安全掃描。

建議工作流：

[source,text]
----
main
  ↑ PR
feature/*
fix/*
docs/*
----

=== 管理者是否也要受規則限制

若允許管理者 bypass，緊急事故時比較方便，但管理者也可能無意間繞過 review 與 CI。

較嚴謹的設定是：

* 平常所有人都走 PR。
* bypass 只給少數管理者或 release automation。
* 緊急變更仍需補 PR、Issue 或事後 review 紀錄。

== Repository Settings 建議

=== General

[source,text]
----
Repository
→ Settings
→ General
----

建議檢查：

* Default branch 是否為 `main`。
* 是否只保留團隊採用的 merge method。
* 勾選 Automatically delete head branches。
* 視需要啟用 Issues、Projects、Wiki、Discussions。
* 避免同時開啟不會使用的功能，減少介面雜訊。

=== Actions

[source,text]
----
Repository
→ Settings
→ Actions
→ General
----

建議檢查：

* 允許哪些 Actions 與 reusable workflows。
* `GITHUB_TOKEN` 預設權限採 read-only，僅對必要 workflow 額外授權。
* Fork PR 是否可以存取 workflow 或 secrets。
* Production deployment 是否需要 Environment reviewer。

=== Security

依 repository 類型評估：

* Dependabot alerts。
* Dependabot security updates。
* Secret scanning。
* Push protection。
* Code scanning。
* Private vulnerability reporting。

部分功能會受 repository visibility 與 GitHub 方案限制。

== GitLab Protected Branch 與 GitHub Ruleset 對照

[cols="30%,35%,35%", options="header"]
|===
|需求 |GitLab |GitHub

|禁止直接 push main
|Protected branch 的 Allowed to push and merge 設為 No one 或特定角色
|Ruleset 要求 Pull request，並限制 bypass actor

|禁止 force push
|Protected branch 關閉 Allowed to force push
|Ruleset / Branch protection 關閉 force push

|要求 CI 通過
|Pipelines must succeed
|Require status checks to pass

|要求核准
|Merge request approval rules
|Require approving reviews

|指定路徑負責人
|Code Owners
|CODEOWNERS + require Code Owner review

|合併前解決討論
|All threads must be resolved
|Require conversation resolution

|限制可合併人員
|Allowed to merge
|Repository permission、Ruleset bypass 與 merge 權限
|===

== 從 GitLab 轉到 GitHub 的操作心法

=== 不要逐字翻譯名稱

最容易混淆的是：

[source,text]
----
Merge Request 不是另一種 Git merge 指令
Pull Request 也不是要求執行 git pull
----

兩者都是平台提供的「變更審查與合併申請」。

=== 先找對應目的，再找設定名稱

例如 GitLab 中的需求是：

[source,text]
----
main 不能直接 push
必須 Pipeline 成功
至少一人 Approve
作者不能自行合併
----

到 GitHub 不應只找完全相同的欄位名稱，而應拆成：

[source,text]
----
Ruleset / Branch protection
+ Repository role
+ Required reviews
+ Required status checks
+ Bypass permissions
----

=== GitHub 的 Assignee 不是 Approver

在 GitLab 習慣把 Assignee 當成主要負責人時，轉到 GitHub 容易誤以為指定 Assignee 就完成審核要求。

正確做法是：

* Assignee 管理責任。
* Reviewer 管理 code review。
* Ruleset 管理是否強制 approval。

=== PR 合併後刪除 branch

啟用：

[source,text]
----
Settings
→ General
→ Pull Requests
→ Automatically delete head branches
----

之後同 repository 的 PR 合併後，GitHub 會嘗試刪除來源 branch。

但本機 branch 不會自動刪除，可執行：

[source,bash]
----
git fetch --prune
git branch -d feature/example
----

== GitHub Repository 建立後檢查清單

=== 建立當下

* Repository 名稱與 visibility 正確。
* 選擇是否初始化 README。
* 選擇正確 `.gitignore`。
* 公開 repository 明確選擇 LICENSE。
* Default branch 使用 `main`。

=== 第一次 push 後

* README 包含 build、test、run 與 deploy 說明。
* 建立至少一個 GitHub Actions build/test workflow。
* 設定 Actions secrets 與 variables。
* 建立 Ruleset 或 Branch protection 保護 `main`。
* 啟用 required status checks。
* 設定至少一名 Reviewer 或 Code Owner。
* 啟用 Automatically delete head branches。
* 設定 Dependabot、secret scanning 等安全功能。
* 確認一般開發者無法直接 push 或 force push `main`。

=== 團隊流程

* 定義 branch 命名方式。
* 定義 commit message 規則。
* 決定主要 merge method。
* 建立 PR template。
* 定義 Reviewer 與 Assignee 責任。
* 定義緊急 bypass 流程。
* 定義 release、tag 與 rollback 流程。

== 建議的簡化團隊規範

[source,text]
----
1. 從 main 建立 feature/*、fix/* 或 docs/* branch。
2. 所有變更透過 PR 合併，不直接 push main。
3. PR 必須有清楚描述與驗證方式。
4. 至少一名非作者 Reviewer Approve。
5. Required checks 全部通過。
6. Review conversation 全部解決。
7. 使用 Squash and merge。
8. 合併後自動刪除遠端 branch。
9. 定期清除本機已合併 branch。
----
