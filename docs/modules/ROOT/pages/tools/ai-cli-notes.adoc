== CLI 使用原則說明

=== Codex CLI（Token 制）

* 每次請求會消耗 input / output tokens
* 多輪對話會重複帶入 context，導致 token 成本上升
* 建議：
- 一次提供完整 context
- 避免拆成過多小問題

=== Claude Code（Session / Quota 制）

* 以時間區段（例如 5 小時）與週使用量為主
* 適合 iterative 開發（反覆調整）
* 建議：
- 可逐步優化
- 不需過度壓縮 prompt

=== Gemini CLI（Request 配額制）

* 以 requests/day 為限制
* 一個 prompt 可能觸發多次 model 呼叫（agent loop）
* 建議：
- 任務一次描述完整
- 減少呼叫次數

'''

== Spec 與 Skill 使用說明

=== 呼叫 CLI 前必須理解

[cols="1,3", options="header"]
|===
| 項目
| 說明

| Spec
| 任務的「一次性完整描述」，讓 CLI 能直接執行，不需猜測需求

| Skill
| 可重複使用的「任務模板」，用來快速產生高品質 Spec

| 為什麼重要
| 若未先整理 Spec / Skill，CLI 會進入猜測與多輪對話，導致 token / request 消耗增加，且結果不穩定

| 核心原則
| Chat 用來釐清需求，CLI 用來一次執行，不應在 CLI 內反覆修需求
|===

'''

=== Spec 與 Skill 比較

[cols="1,2,3", options="header"]
|===
| 類型
| 定義
| 特性

| Spec
| 單次任務的完整指令描述
| - 一次性使用 +
- 任務導向 +
- 需包含完整 context +
- 直接給 CLI 執行

| Skill
| 可重複使用的任務模板（Spec 的抽象化）
| - 可重複使用 +
- 結構固定 +
- 用於快速產生 Spec +
- 提升一致性與效率
|===

'''

=== Spec 撰寫原則

[cols="1,3", options="header"]
|===
| 原則
| 說明

| 完整性
| 必須包含任務目標、輸入、輸出、限制，避免 CLI 猜測需求

| 明確性
| 每個要求需具體，例如「使用 JdbcTemplate」而非「優化資料庫」

| 一次完成
| 避免拆成多輪指令，降低 token / request 消耗

| 限制清楚
| 明確技術限制（如 Java 版本、不可使用框架），避免偏離需求

| Context 控制
| 僅提供必要檔案與資訊，避免過多無關內容
|===

'''

=== Skill 設計原則

[cols="1,3", options="header"]
|===
| 原則
| 說明

| 可重用性
| 能套用於多個專案或類似任務（例如 refactor、optimize）

| 結構固定
| 使用固定模板（任務目標 / 輸入 / 要求 / 輸出 / 限制）

| 可擴充性
| 可依需求補充細節，而不破壞原有結構

| 任務分類
| 依類型建立 skill，例如：
- refactor-service
- optimize-sql
- fix-encoding

| 降低思考成本
| 使用 skill 時，只需填入內容，不需重新思考 prompt 結構
|===

'''

=== 實務建議

[cols="1,3", options="header"]
|===
| 項目
| 建議

| 開發流程
| ChatGPT 討論 → 產出 Spec → CLI 執行

| Spec 使用時機
| 每次 CLI 執行前皆應先整理 Spec

| Skill 使用時機
| 當任務類型重複出現時，將 Spec 抽象為 Skill

| 成本控制
| 良好的 Spec 可顯著降低 token（Codex）或 request（Gemini）消耗

| 品質提升
| Skill 可確保不同任務輸出格式一致，降低維護成本
|===

'''

=== 核心結論

[source,text]
----
Spec / Skill 品質
    ＞ CLI 工具選擇
    ＞ 模型差異
----

== CLI 最終最佳流程

[cols="1,3", options="header"]
|===
| 步驟
| 說明

| 1
| ChatGPT：討論需求（自由描述，不需結構化）

| 2
| ChatGPT：轉成 CLI spec（結構化、可執行）

| 3
| CLI：一次執行（避免多輪 request / token 重複消耗）

| 4
| 若需微調，再回 ChatGPT 修 spec，而非直接在 CLI 多輪修改
|===

'''

== CLI Spec 範例（可執行格式）

[source,text]
----
[任務目標]
重構某段 Java service，使其可讀性提升並符合 Spring Boot 實務

[輸入]
- 檔案：UserService.java
- 目前問題：
  1. method 過長
  2. SQL 寫死
  3. logging 不一致

[要求]
1. 拆分 method（單一責任）
2. 改用 JdbcTemplate
3. 加入 log4j logging
4. 保持原有功能不變

[輸出]
- 提供完整修改後 code
- 提供 diff（舊 vs 新）
- 說明修改原因

[限制]
- Java 8 相容
- 不使用新框架
----

'''
