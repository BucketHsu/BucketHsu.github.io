本頁整理自架大型語言模型推論服務、Runtime 與模型選型、HTTPS 代理，以及 GitLab Merge Request AI Code Review 的通用架構。

文件刻意使用通用主機名稱、服務名稱、路徑與 Token 變數，不包含任何實際公司網路、Registry、憑證、帳號或存取權杖。

== 適用範圍

本指南適合下列情境：

* 在具備 NVIDIA GPU 的 Linux 主機提供內部推論 API。
* 使用 OpenAI 相容介面整合現有工具。
* 透過 Nginx 提供 HTTPS、驗證與流量控管。
* 在 GitLab Merge Request Pipeline 執行程式碼初步審查。
* 將模型審查結果寫回 MR Note 或行內 Discussion。

本指南不代表 AI 可以取代人工 Reviewer，也不保證模型能判斷實際業務邏輯、法規或需求正確性。

[WARNING]
====
[WARNING]
====
模型版本、Image Tag、硬體支援與授權會持續變動。正式部署前必須重新查閱官方 Model Card、License、Container Registry 與 Runtime 支援矩陣。
====

不得將 NGC API Key、GitLab Access Token、AI API Token、私鑰、正式憑證、內網位址或真實專案原始碼提交至公開 Repository。
====

== 架構概觀

[source,text]
----
開發人員建立或更新 Merge Request
                │
                ▼
GitLab MR Pipeline
                │
                ├── 取得 MR Diff
                ├── 過濾不需審查的檔案
                └── 分批建立 Prompt
                │
                ▼
AI Code Review Job
                │
                ▼
https://ai.example.test/v1
                │
                ▼
Nginx
                │
                ├── TLS
                ├── Token 驗證
                ├── Rate Limit
                └── Access Log
                │
                ▼
OpenAI 相容推論服務
                │
                ▼
GPU 與模型
----

主要責任如下：

[cols="28%,72%", options="header"]
|===
|元件 |責任

|推論服務
|載入模型、管理 GPU 與記憶體，並提供 `/v1/models`、`/v1/chat/completions` 與健康檢查。

|Nginx
|提供 TLS、驗證、流量限制與反向代理，不負責 GitLab 權限與 MR 邏輯。

|AI Code Review Job
|取得 MR Diff、建立 Prompt、驗證模型輸出並回寫 GitLab。

|GitLab
|管理 Pipeline、CI/CD Variables、Merge Request、Protected Branch 與 Merge Check。

|人工 Reviewer
|判斷需求、業務邏輯、風險、AI 誤判及是否允許 Merge。
|===

== 從模型到 HTTP API

模型權重本身不能直接被 GitLab Runner 呼叫，仍需由推論引擎處理：

* Tokenizer 與 Chat Template。
* GPU、記憶體與 KV Cache。
* Batch、排程與併發。
* Sampling、停止條件與最大輸出長度。
* HTTP API、健康檢查與使用量資訊。

建議至少提供下列端點：

[source,text]
----
GET  /v1/models
POST /v1/chat/completions
GET  /v1/health/ready
----

呼叫端應先讀取 `/v1/models` 的實際模型 ID，不要只根據 Container Image 名稱推測 `model` 值。

== GPU Container 前置驗證

確認主機已安裝 NVIDIA Driver、Docker Engine 與 NVIDIA Container Toolkit。

[source,bash]
----
nvidia-smi

docker run --rm --gpus all \
  nvidia/cuda:12.8.0-base-ubuntu24.04 \
  nvidia-smi
----

若 Container 內無法看到 GPU，應先修正 Driver、Runtime 或 Docker 設定，不要直接排查模型服務。

|封裝模型、Runtime、Profile 與 API
|NVIDIA GPU、希望降低 Runtime 組裝成本、需要標準化部署

== 新模型第一時間導入策略

若主要需求是「模型發布後盡快在自有硬體測試」，不應只依賴單一封裝式 Runtime。較實際的順序是：

[source,text]
----
新模型發布
    │
    ├─ 1. Transformers：先確認權重、Tokenizer、Chat Template 可正常載入
    │
    ├─ 2. SGLang / vLLM：有原生支援後改成正式 API 服務
    │
    ├─ 3. llama.cpp：需要 GGUF、低記憶體或跨平台時評估
    │
    └─ 4. NIM / TensorRT-LLM：官方最佳化成熟後再比較效能與維運成本
----

[cols="20%,18%,27%,35%", options="header"]
|===
|Runtime |新模型跟進速度 |主要用途 |判斷原則

|Transformers
|通常最快
|Day-0 功能驗證、Fallback
|只要模型已整合 Transformers，或 Model Repository 提供可信任的自訂程式碼，就可能先行測試；不應直接視為正式高併發架構

|SGLang
|很快
|新模型 Serving、Coding/Agent、Speculative Decoding
|若新模型已被 SGLang 支援，適合直接提供 OpenAI 相容 API；對特定模型的最佳化可能比通用 Runtime 更早出現

|vLLM
|很快
|正式 OpenAI API、高吞吐、多使用者
|模型架構與量化格式已支援時通常是穩定的正式服務候選

|llama.cpp
|快，但依 GGUF 與架構支援
|量化、省記憶體、CPU/GPU 混合
|適合工作站與低資源環境；需確認 GGUF 轉換與量化品質

|NVIDIA NIM
|依 NVIDIA 發布時程
|標準化 NVIDIA 部署
|不必自行組合 Runtime，但新模型可能需要等待對應 Image、Model Profile 或 model-free NIM 支援

|TensorRT-LLM
|依模型整合與最佳化程度
|固定模型後追求 NVIDIA GPU 效能
|較適合模型已選定後再投入 Engine、量化與版本調校
|===

[IMPORTANT]
====
「第一時間可載入」不等於「第一時間適合上正式環境」。新模型仍要完成 License、模型來源、Prompt、結構化輸出、Context、記憶體、長時間穩定度與 Code Review 固定測試集驗證。
====

== 上層服務避免綁死 Runtime

Spring Boot、GitLab CI 或其他呼叫端應盡量依賴共同 API Contract，而不是直接寫死某個 Runtime 的專有行為。

[source,text]
----
GitLab CI / Chat / 其他服務
            │
            ▼
        ai-infra
            │
     OpenAI 相容 API
            │
     ┌──────┼────────┐
     ▼      ▼        ▼
   vLLM   SGLang    NIM
            │
            ▼
      Hugging Face Model
----

例如應把 Base URL 與 Model ID 外部化：

[source,properties]
----
ai.base-url=http://llm-runtime:8000/v1
ai.model=<MODEL_ID>
----

這樣切換 vLLM、SGLang 或 NIM 時，上層 Code Review 邏輯通常只需調整設定或少量 Runtime Adapter，而不是重新改寫整個流程。

== Ollama

=== 啟動服務

[source,bash]
----
docker volume create ollama

docker run -d \
  --name ollama \
  --restart unless-stopped \
  --gpus all \
  -v ollama:/root/.ollama \
  -p 127.0.0.1:11434:11434 \
  ollama/ollama:<固定版本>
----

正式環境不建議長期追蹤 `latest`。應固定已測試的 Image Tag，並記錄 CPU 架構、CUDA、模型名稱與 Ollama 版本。

=== 下載與執行模型

[source,bash]
----
docker exec -it ollama ollama pull <模型名稱>
docker exec -it ollama ollama run <模型名稱>
----

=== API 驗證

[source,bash]
----
curl --fail --silent http://127.0.0.1:11434/api/tags

curl --fail --silent http://127.0.0.1:11434/api/chat \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<模型名稱>",
    "messages": [
      {"role": "user", "content": "請只回覆 OK"}
    ],
    "stream": false
  }'
----

若整合工具要求 OpenAI API，需確認目前 Ollama 版本實際支援的 `/v1/models` 與 `/v1/chat/completions` 行為；不能只改 URL。

=== 維運指令

[source,bash]
----
docker ps --filter name=ollama
docker logs -f ollama
docker stop ollama
docker start ollama
----

刪除 Container 不等於刪除 `ollama` Volume。執行 `docker volume rm ollama` 前必須確認模型不再需要。

== llama.cpp

=== 準備 GGUF

[source,bash]
----
mkdir -p /opt/llama.cpp/models
ls -lh /opt/llama.cpp/models
----

應保存模型來源、Model Card、License、GGUF 量化方式與檔案雜湊。不同量化等級會影響記憶體、速度及 Code Review 品質。

=== CUDA Server 啟動

[source,bash]
----
docker run -d \
  --name llama-cpp \
  --restart unless-stopped \
  --gpus all \
  -p 127.0.0.1:8080:8080 \
  -v /opt/llama.cpp/models:/models:ro \
  ghcr.io/ggml-org/llama.cpp:server-cuda \
  -m /models/<模型>.gguf \
  --host 0.0.0.0 \
  --port 8080 \
  -c 8192 \
  --n-gpu-layers 99
----

[cols="30%,70%", options="header"]
|===
|參數 |用途

|`-m`
|GGUF 模型檔案。

|`-c`
|Context 上限。提高時通常會增加 KV Cache 記憶體。

|`--n-gpu-layers`
|放入 GPU 的 Layer 數；降低可減少 GPU 記憶體，但可能降低速度。

|`--host`
|Container 內監聽位址。即使使用 `0.0.0.0`，Host 端仍建議只映射 `127.0.0.1`，再由受控 Proxy 對外提供服務。
|===

=== API 與健康檢查

[source,bash]
----
curl --fail http://127.0.0.1:8080/health
curl --fail http://127.0.0.1:8080/v1/models
----

== Transformers

Transformers 適合作為新模型剛發布時的第一層相容性驗證。若其他推論 Runtime 尚未支援新架構，可先確認權重、Tokenizer、Chat Template 與基本 Generation 是否正常。

=== 直接載入模型

[source,python]
----
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "<Hugging-Face-模型-ID>"

tokenizer = AutoTokenizer.from_pretrained(model_id)
model = AutoModelForCausalLM.from_pretrained(
    model_id,
    device_map="auto",
    torch_dtype="auto"
)
----

只有 Model Repository 確實需要自訂程式碼且來源可信任時才考慮：

[source,python]
----
AutoModelForCausalLM.from_pretrained(
    model_id,
    device_map="auto",
    torch_dtype="auto",
    trust_remote_code=True,
    revision="<固定 Commit SHA>"
)
----

[WARNING]
====
`trust_remote_code=True` 代表允許執行 Model Repository 提供的 Python 程式碼。正式環境應審查來源並固定 `revision`，不要對未知 Repository 無條件開啟。
====

=== Transformers Serve

新版 Transformers 提供實驗性的 `transformers serve`，可提供 OpenAI SDK 相容介面，適合評估、實驗與中等負載自架；大規模正式 Serving 仍應優先比較 vLLM、SGLang 等專用 Runtime。

[source,bash]
----
pip install 'transformers[serving]'
transformers serve
----

可用端點依版本確認，常見包含：

[source,text]
----
/v1/models
/v1/chat/completions
/v1/responses
----

== vLLM

=== 快取與權限

[source,bash]
----
mkdir -p /opt/vllm/huggingface-cache
export HUGGING_FACE_HUB_TOKEN='<不要寫入 Git>'
----

=== 啟動 OpenAI Server

[source,bash]
----
docker run -d \
  --name vllm \
  --restart unless-stopped \
  --runtime nvidia \
  --gpus all \
  --ipc=host \
  -p 127.0.0.1:8000:8000 \
  -v /opt/vllm/huggingface-cache:/root/.cache/huggingface \
  -e HUGGING_FACE_HUB_TOKEN \
  vllm/vllm-openai:<固定版本> \
  --model <Hugging-Face-模型-ID> \
  --host 0.0.0.0 \
  --port 8000 \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.80
----

多 GPU 模型可依支援情況加入：

[source,bash]
----
--tensor-parallel-size <GPU 數量>
----

[cols="34%,66%", options="header"]
|===
|參數 |用途

|`--model`
|Hugging Face ID 或 Container 內模型路徑。

|`--max-model-len`
|輸入與輸出合計 Context 上限，不應無條件設定為模型標示的最大值。

|`--gpu-memory-utilization`
|vLLM 可使用的 GPU 記憶體比例。需保留 Driver、其他服務與尖峰空間。

|`--tensor-parallel-size`
|將模型分散到多張 GPU；GPU 數量、拓樸及模型結構需相容。

|`--ipc=host`
|提供較大的共享記憶體空間，降低 PyTorch 或 NCCL 因預設 `/dev/shm` 過小而失敗的機率。
|===

[WARNING]
====
ARM64 或特殊整合式 GPU 平台不能直接沿用 x86_64 測試結論。必須確認 Image、PyTorch、CUDA、模型架構與硬體支援。
====

== SGLang

SGLang 是與 vLLM 同級的推論 Serving Runtime，重點包含高吞吐 Serving、Radix/Prefix Cache、結構化輸出、Tool/Agent 工作負載與 Speculative Decoding。對剛發布的新模型，若 SGLang 已完成架構整合，可直接從 Hugging Face Model ID 啟動，不需要等待 NIM 專用 Image。

=== 啟動 Server

以下使用 SGLang 官方常見的 `launch_server` 形式；實際 Container Image、版本與模型參數仍應依當版文件固定：

[source,bash]
----
python3 -m sglang.launch_server \
  --model-path <Hugging-Face-模型-ID> \
  --host 0.0.0.0 \
  --port 30000
----

若模型需要 Hugging Face Token，應由環境變數或 Secret 注入，不要提交到 Git。

=== OpenAI 相容 API

SGLang Server 可提供 OpenAI 相容端點。啟動後至少驗證：

[source,bash]
----
curl --fail http://127.0.0.1:30000/v1/models

curl --fail --silent \
  --request POST \
  --header 'Content-Type: application/json' \
  --data '{
    "model": "<MODEL_ID>",
    "messages": [
      {"role": "user", "content": "請只回覆 READY"}
    ],
    "temperature": 0,
    "max_tokens": 32
  }' \
  http://127.0.0.1:30000/v1/chat/completions
----

=== Speculative Decoding 與 MTP

部分新模型提供 MTP（Multi-Token Prediction）或其他 Draft/Speculative Decoding 能力，可讓 Runtime 一次驗證多個候選 Token，進而提高 Decode 吞吐。

但效能提升高度依賴：

* 模型本身是否提供可用的 Draft/MTP Head。
* SGLang 版本是否支援該模型的 Speculative 方法。
* Acceptance Rate。
* Prompt 與輸出型態。
* Context 長度與 Batch。
* 量化格式與 Kernel。

因此不能把特定測試中出現的最高 tok/s 當成所有 Chat 或 Code Review 工作負載的固定速度。正式導入應使用自己的 Java、Spring Boot、SQL 與 Git Diff 測試集量測。

=== 與 vLLM 的選擇

[cols="22%,39%,39%", options="header"]
|===
|項目 |SGLang |vLLM

|新模型支援
|部分熱門新模型會快速加入，適合追蹤 Day-0/Day-1 支援
|同樣更新快速，模型架構進入支援矩陣後適合正式服務

|OpenAI API
|支援
|支援

|主要優勢
|Prefix/Radix Cache、Speculative Decoding、Agent/Coding 工作負載與快速模型整合
|成熟 Serving、生態完整、Continuous Batching、廣泛 OpenAI API 應用整合

|選擇方式
|某模型在 SGLang 有明確最佳化或實測優勢時優先
|一般正式 API、既有整合成熟或該模型支援較完整時優先
|===

== TensorRT-LLM

=== 啟動方式

[source,bash]
----
trtllm-serve <模型-ID-或模型路徑> \
  --host 0.0.0.0 \
  --port 8000
----

多 GPU 可依版本及模型支援加入：

[source,bash]
----
--tp_size <GPU 數量>
----

某些模型可直接由 `trtllm-serve` 載入，某些情境則需要先轉換權重或建立最佳化 Engine。若使用 Engine，通常需固定：

* 模型與權重版本。
* 精度或量化設定。
* Tensor Parallel 數量。
* 最大 Batch。
* 最大 Sequence Length。
* TensorRT-LLM 與 CUDA 版本。

上述任一項改變後，都可能需要重新建置 Engine。

=== 驗證

[source,bash]
----
curl --fail http://127.0.0.1:8000/health
curl --fail http://127.0.0.1:8000/v1/models
curl --fail http://127.0.0.1:8000/version
curl --fail http://127.0.0.1:8000/metrics
----

== NVIDIA NIM

=== 登入 NGC

[source,bash]
----
docker login nvcr.io
----

Username 通常使用 `$oauthtoken`，Password 輸入 NGC API Key。API Key 不得寫入 Shell Script、Compose 或 Git。

=== 單一模型啟動

[source,bash]
----
export NGC_API_KEY='<不要寫入檔案>'
export NIM_IMAGE='<NIM Image:固定版本>'

docker run -d \
  --name nim-llm \
  --restart unless-stopped \
  --gpus all \
  --shm-size=64g \
  -e NGC_API_KEY \
  -e NIM_MAX_MODEL_LEN=8192 \
  -e NIM_LOG_LEVEL=INFO \
  -p 127.0.0.1:8000:8000 \
  -v /opt/nim/cache:/opt/nim/.cache \
  "${NIM_IMAGE}"
----

首次啟動可能下載模型或建立硬體 Profile。Container 顯示 `Up` 不代表服務 Ready。

[source,bash]

== DGX Spark 建議策略

DGX Spark 的重點是 128GB Unified Memory 帶來的模型容量與 Context 空間，不應只用桌機顯示卡的單人 tok/s 判斷價值。對單台 Spark 的內部 Code Review 平台，可採分階段策略：

[source,text]
----
新模型剛發布
    ↓
Transformers / SGLang 先做相容性與能力測試
    ↓
SGLang / vLLM 提供穩定 OpenAI 相容 API
    ↓
固定 32K Context 起跑並量測實際 Git Diff
    ↓
再評估 64K / 128K、Speculative Decoding、MTP、量化
    ↓
NVIDIA NIM / TensorRT-LLM 有成熟最佳化後做 A/B Test
----

對 Code Review 應優先量測：

* TTFT（Time To First Token）。
* Decode tok/s。
* 單批推論時間。
* 整個 MR 的總處理時間。
* 多人或多 Job 併發時的吞吐。
* 32K、64K、128K Context 下的記憶體占用。
* NVFP4、FP8、BF16 或其他量化對 Review 品質的影響。

不要把網路上特定 Prompt 的 50～70 tok/s 直接當成自己的預期值。Speculative Decoding 對可預測、重複或 Edit-heavy 輸出可能特別有效，但實際 Java/Spring Boot Code Review 應以固定測試集量測。

== Kimi K3

Kimi K3 是 Moonshot AI 於 2026 年 7 月發布的開放權重原生多模態 Agent 模型。官方資料列出的主要特徵包括：

* 2.8T 總參數。
* 每個 Token 約啟用 104B 參數。
* Stable LatentMoE，從 896 個 Expert 中啟用 16 個。
* Kimi Delta Attention 與 Attention Residuals。
* 原生 Vision。
* 最長 100 萬 Token Context。
* 著重長時間 Coding、Agent、知識工作與推理。

[IMPORTANT]
====
MoE 的 104B 啟用參數只代表每個 Token 的主要計算量，不代表只需載入 104B 權重。完整 2.8T 權重、KV Cache、Runtime、Expert Parallel 與多模態元件仍會造成極高的儲存與記憶體需求。
====

=== 對現有平台的意義

Kimi K3 應加入模型趨勢與能力比較，但目前不宜直接列為單台 DGX Spark 的日常 Code Review 候選，原因包括：

* 完整權重規模遠高於目前 26B、32B、49B、70B 候選。
* 即使採 8-bit 或更低精度，完整權重與 Runtime 需求仍非常高。
* 100 萬 Token Context 不代表正式服務應直接配置到上限；KV Cache 成本仍需估算。
* 自建需要確認 Transformers、vLLM、SGLang、TensorRT-LLM 或其他 Runtime 的實際支援。
* 可能需要多節點、多 GPU、Expert Parallel 或由推論供應商提供託管服務。
* 自訂 License、商業使用、散布與衍生模型條款需單獨審查。

較合理的評估方式：

. 先使用官方或受控託管 API，對固定 Code Review 測試集進行能力比較。
. 確認輸出 Schema、行號、誤報、漏報與長 Repository 理解能力。
. 再評估可用的壓縮、量化或官方推論方案。
. 最後才進行硬體容量、成本、授權與維運評估。

官方參考：

* https://huggingface.co/moonshotai/Kimi-K3[Kimi K3 Model Card]
* https://arxiv.org/abs/2607.24653[Kimi K3 Technical Report]

== Code Review 模型評估

[cols="29%,71%", options="header"]
|===
|指標 |說明

|具體問題準確率
|模型回報的問題是否能由 Diff 與必要上下文直接證實。

|誤報率
|是否大量輸出命名、格式、偏好或無法驗證的「建議確認」。

|漏報率
|固定測試集中預先放入的正確性、資安、相容性與資源問題是否被發現。

|行號正確率
|檔案、Line Type 與行號能否建立有效 GitLab Discussion。

|JSON 完整率
|能否穩定遵循 Schema，不混入 `<think>`、Markdown 或截斷 JSON。

|單批延遲
|同一 Prompt、Diff 與輸出上限下的 API 時間。

|MR 總時間
|包含分批、模型推論、GitLab API 與回寫的完整 Job 時間。

|Context 使用
|是否容易因 system prompt、專案規範、Diff 與輸出預留而超限。

|資源使用
|Ready 與推論尖峰的 GPU、記憶體、功耗、溫度與磁碟快取。

|授權與資料治理
|模型、基礎模型、Runtime、API 與資料流是否符合要求。
|===

=== 固定測試集

至少準備：

* 沒有問題的正常 MR。
* 單一明確錯誤的小型 MR。
* Java 版本不相容。
* SQL Injection、XSS 或權限缺漏。
* 空值、資源未關閉與交易問題。
* 純 CRLF／LF 或格式異動。
* Lockfile、產生檔與二進位檔。
* 多 Commit、再次 Push 與 Discussion 更新。
* 大型 Diff、跨多檔案與多批次。

== 模型與硬體的判斷原則

=== Dense 與 MoE

Dense 模型通常讓每個 Token 經過大部分參數；MoE 由 Router 選擇部分 Expert。比較 MoE 時必須同時看：

* 總參數。
* 啟用參數。
* Expert 數量及每 Token 啟用數。
* 完整權重精度與量化。
* Expert Parallel／Tensor Parallel 需求。
* KV Cache 與 Context。
* Runtime Overhead。

=== Context Length

模型標示的最大 Context 不應直接作為服務預設值。Code Review 的 Context 包含：

[source,text]
----
system prompt
+ 專案規範
+ MR 資訊
+ Diff
+ Chat Template 額外 Token
+ 預留輸出 Token
----

優先使用：

* 排除產生檔、Lockfile、壓縮檔及二進位檔。
* 依檔案或 Hunk 分批。
* 每批只提供必要上下文。
* 限制單次輸出長度。
* 對過大的 MR 要求拆分。

== 最終選型順序

. 確認 License、資料流與供應來源可接受。
. 確認 Image、Runtime 與硬體可啟動並 Ready。
. 驗證 `/v1/models`、Chat Completion 與健康檢查。
. 驗證固定 JSON Schema 與行號。
. 使用相同測試集比較誤報、漏報與具體問題準確率。
. 記錄單批、MR 總時間、記憶體與功耗。
. 驗證長時間運行、重新啟動與版本升級。
. 才決定日常模型、品質基準模型與備援模型。

[NOTE]
====
模型排行榜與廠商 Benchmark 只能作為初篩。實際 Code Review 結果必須以相同 Prompt、相同 Diff、相同 Schema、相近 Context 與固定測試集比較。
====

=== 多模型設定切換

若有多個候選模型，但同一時間只啟動一個模型，可將共用機密與各模型參數分開保存：

[source,text]
----
nim/
├── docker-compose.yml
├── .env
├── models/

== Nginx HTTPS 反向代理

推論服務建議只監聽 `127.0.0.1` 或內部 Container Network，再由 Nginx 對外提供 TLS。

[source,nginx]
----
limit_req_zone $binary_remote_addr zone=ai_api:10m rate=5r/s;

server {
    listen 443 ssl;
    server_name ai.example.test;

    ssl_certificate     /etc/nginx/certs/server.crt;
    ssl_certificate_key /etc/nginx/certs/server.key;

    location = /nginx-health {
        access_log off;
        return 200 "ok\n";
    }

    location /v1/ {
        if ($http_authorization != "Bearer ${AI_API_TOKEN}") {
            return 401;
        }

        limit_req zone=ai_api burst=10 nodelay;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

        proxy_read_timeout 300s;
        proxy_pass http://inference:8000;
    }
}
----

[WARNING]
====
Nginx `if` 搭配固定 Bearer Token 只適合小型或過渡環境。正式平台應考慮 Token 雜湊、個別用戶或專案識別、到期日、撤銷、用量限制、稽核及密鑰輪替。
====

自簽憑證若由內部 CA 簽發，應將 CA 加入 Runner 或 Code Review Image 的信任鏈，不要以 `curl -k` 或關閉 TLS 驗證作為正式解法。

== GitLab 權限設計

AI Code Review 只應取得完成工作所需的最低權限。

建議原則：

* 優先使用 Project Access Token 或 Group Access Token，不使用管理者個人的 Personal Access Token。
* Token 設定明確到期日。
* Role 與 Scope 採最小權限。
* 不允許 AI Token 取得 Repository 寫入、管理員或 Runner 管理權限。
* 定期檢查使用紀錄與最後使用時間。
* 在 Token 到期前完成輪替，不延後處理。

== Prompt 與輸出格式

為便於程式驗證，建議要求模型回傳固定 JSON：

[source,json]
----
{
  "summary": "整體摘要",
  "findings": [
    {
      "severity": "high",
      "path": "src/main/java/example/Service.java",
      "line": 42,
      "title": "問題標題",
      "message": "問題說明",
      "suggestion": "修正建議"
    }
  ]
}
----

呼叫端必須驗證：

* JSON 是否可解析。
* 欄位是否符合 Schema。
* `path` 是否屬於本次 Diff。
* `line` 是否能定位到有效的新行。
* Severity 是否在允許範圍。
* Finding 數量是否超過上限。
* 回應是否包含 Token、Prompt 或機密內容。

模型輸出不能直接當成 Shell、SQL 或 Git 指令執行。

== Note 與行內 Discussion

MR Note 適合：

* 整體摘要。
* 無法精確定位行號的建議。
* 模型服務失敗或審查範圍不足的說明。

行內 Discussion 適合：

* 能對應到本次 Diff 新行的問題。
* 需要 Reviewer 明確處理或 Resolve 的缺陷。

建立行內 Discussion 前，通常需要：

* Base SHA。
* Start SHA。
* Head SHA。
* 檔案舊路徑與新路徑。
* 舊行號或新行號。

定位失敗時，應降級成 MR Note，不應讓整個 Pipeline 因單一 Comment 失敗。

== Merge 阻擋策略

AI 結果可採三種模式：

[cols="20%,32%,48%", options="header"]
|===
|模式 |行為 |適用情境

|提示
|AI Job 永遠不阻擋 Merge。
|導入初期、觀察誤報率。

|條件阻擋
|只有高嚴重度問題或未解決 Discussion 阻擋。
|已累積足夠準確度與團隊共識。

|強制阻擋
|AI 服務失敗或任何 Finding 都阻擋。
|通常不建議，容易受模型與基礎設施波動影響。
|===

較穩健的策略是：

* AI 服務不可用時明確標示「未完成 AI 審查」。
* 不把服務逾時誤標為 PASS。
* 對高風險 Repository 保留人工 Approval 與 Required Pipeline。
* 不允許作者以 AI PASS 取代其他 Reviewer。

== 驗證流程

=== API 驗證

[source,bash]
----
export AI_API_URL='https://ai.example.test/v1'
export AI_API_TOKEN='<DO_NOT_COMMIT>'

curl --fail --silent \
  --header "Authorization: Bearer ${AI_API_TOKEN}" \
  "${AI_API_URL}/models"
----

=== GitLab 驗證

測試 MR 至少包含：

* 一個可被審查的文字檔。
* 一個應被排除的檔案。
* 一個可精確定位行號的明顯問題。
* 一個沒有 Finding 的正常修改。
* 超過單批大小限制的 Diff。

確認：

* Job 只在 MR Pipeline 執行。
* 變數可正確取得且不出現在 Job Log。
* MR Note 不會每次執行都重複累積。
* 已修正的行內 Discussion 能正確更新或 Resolve。
* API 失敗、格式錯誤與逾時均有明確狀態。

== 常見問題

[cols="30%,30%,40%", options="header"]
|===
|問題 |可能原因 |處理方式

|NIM 長時間未 Ready
|模型仍在下載、GPU 記憶體不足、Context 過大或 Image 與硬體不相容。
|檢查 Container Log、GPU、模型快取、Image 支援資訊與啟動參數。

|API 回傳 404
|Base URL 缺少 `/v1`，或 Nginx `proxy_pass` 路徑組合錯誤。
|分別測試 Nginx 與 Backend 的 `/v1/models`。

|TLS 驗證失敗
|Runner 或 Image 不信任內部 CA。
|將 CA 安裝至信任鏈並重建 Image，不使用 `-k`。

|Pipeline 取不到 Token
|Variable Scope、Protected、Environment Scope 或 Group 繼承不符。
|檢查 Pipeline 類型與 Variable 設定；不要在 Log 輸出 Token。

|行內 Discussion 建立失敗
|SHA、Path 或行號不是本次 Diff 的有效位置。
|重新取得 MR Versions，定位失敗則改寫 MR Note。

|模型輸出不是 JSON
|Prompt 不夠明確、輸出被截斷或模型不穩定。
|降低輸入大小、增加 Schema 驗證並限制重試次數。

|同一問題重複留言
|缺少 Finding Fingerprint 或同步機制。
|以 Repository、MR、Path、Line 與 Finding 內容建立穩定識別碼。
|===

== Token 輪替

輪替順序建議如下：

. 建立新 Token，保留舊 Token 暫時有效。
. 在受控環境驗證新 Token。
. 更新 CI/CD Variable 或 Secret Store。
. 執行測試 MR。
. 確認成功後撤銷舊 Token。
. 檢查舊 Token 是否仍有使用紀錄。

Token 不應透過 Chat、Issue、Wiki、README、Job Artifact 或截圖傳遞。

== 監控與稽核

至少記錄：

* 請求時間與回應狀態。
* 呼叫來源專案的匿名或受控識別碼。
* 模型 ID 與服務版本。
* Input／Output Token 數量。
* 延遲、逾時與錯誤類型。
* Finding 數量與嚴重度統計。

不應記錄：

* 完整 Authorization Header。
* Access Token。
* 未遮罩的 Prompt 與原始碼全文。
* 私鑰與憑證密碼。
* 個人 Email 或帳號，除非有明確稽核需求與保存政策。

== 公開前安全檢查

將內部文件轉為公開筆記前，至少搜尋：

[source,bash]
----
git grep -nE '10\.[0-9]+\.[0-9]+\.[0-9]+'
git grep -nE '172\.(1[6-9]|2[0-9]|3[01])\.[0-9]+\.[0-9]+'
git grep -nE '192\.168\.[0-9]+\.[0-9]+'
git grep -niE '(password|token|secret|api[_ -]?key|authorization)'
git grep -nE '[A-Za-z]:\\Users\\|/home/[A-Za-z0-9._-]+'
----

也要人工檢查：

* 公司、客戶、部門與系統名稱。
* 內部 DNS、IP、Port 與 Registry。
* GitLab Group、Project、Runner 與帳號名稱。
* Container Image 與私有 Base Image。
* 真實憑證、CA、Fingerprint 與私鑰。
* 截圖中的瀏覽器帳號、組織名稱、Avatar、URL 與 API Key。
* Prompt、Diff 或 Log 中的業務資料。
