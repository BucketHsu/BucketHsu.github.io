== 更新原則

套件更新應分成「盤點、更新、驗證、檢視異動」四個階段。不要一次跨越多個大版號，也不要在尚未確認建置與測試結果前提交 lockfile。

更新前先確認：

* Git 工作目錄沒有混入無關異動。
* 專案使用的 Node.js、pnpm、Java 與 Maven 版本符合建置規範。
* 已閱讀目標套件的 release notes、migration guide 與已知不相容變更。
* 私有 registry、內部套件名稱、內部網址、Token、帳號與憑證不得貼入公開 issue、commit message 或建置紀錄。

[NOTE]
====
更新工具只負責調整版本或解析依賴，不能取代編譯、單元測試、整合測試與實際功能驗證。
====

== pnpm 套件更新

=== 1. 確認執行環境

[source,bash]
----
node -v
pnpm -v
----

若 `package.json` 已設定 `packageManager`，應使用專案指定的 pnpm 版本，避免不同 pnpm 大版號產生不相容的 lockfile。

=== 2. 查看可更新套件

[source,bash]
----
pnpm outdated
----

只查看目前 `package.json` 版本範圍允許的更新：

[source,bash]
----
pnpm outdated --compatible
----

Workspace 專案可檢查所有 package：

[source,bash]
----
pnpm outdated --recursive
----

=== 3. 依既有版本範圍更新

[source,bash]
----
pnpm update
----

此命令會依 `package.json` 允許的版本範圍更新所有依賴，並更新 `pnpm-lock.yaml`。`package.json` 是否發生異動取決於更新方式、版本範圍與 pnpm 設定，因此仍須以 `git diff` 確認。

=== 4. 更新指定套件

[source,bash]
----
pnpm update vite
pnpm update react react-dom
----

建議優先逐組更新相關套件，例如 `react` 與 `react-dom` 一起處理，以便縮小問題範圍。

=== 5. 跨大版號更新

[source,bash]
----
pnpm update vite --latest
----

`--latest` 會依套件的 `latest` tag 更新，可能跨越大版號並調整 `package.json` 的版本範圍。執行前應先閱讀 migration guide，並避免一次更新多個無關的核心套件。

需要互動式選擇套件時可使用：

[source,bash]
----
pnpm update --interactive
----

=== 6. 安裝並確認 lockfile

[source,bash]
----
pnpm install
pnpm install --frozen-lockfile
----

第一個命令安裝依賴，必要時會同步更新 lockfile；第二個命令不允許變更 lockfile，適合模擬 CI 的安裝檢查。

=== 7. 處理 lockfile 異常

先確認專案指定的 pnpm 版本，再依錯誤類型處理。lockfile 內容損壞或缺漏時，可先嘗試：

[source,bash]
----
pnpm install --fix-lockfile
----

pnpm 11 提供以下命令，可清除 workspace 內的 `node_modules`，並一併移除 `pnpm-lock.yaml`：

[source,bash]
----
pnpm clean --lockfile
pnpm install
----

[WARNING]
====
`pnpm clean --lockfile` 會刪除 `node_modules` 與 lockfile，應視為最後手段。執行前先保留 Git 異動，並確認重新解析全部依賴的風險。pnpm 10 沒有 `clean` 命令；若出現 `Command "clean" not found`，請勿照搬 pnpm 11 的處理方式。
====

=== 8. 執行品質檢查

實際指令依 `package.json` 的 scripts 為準：

[source,bash]
----
pnpm lint
pnpm test
pnpm build
----

`pnpm build` 只會執行 `scripts.build`，不是更新套件。若專案未定義對應 script，會出現找不到命令或 script 的錯誤。

若專案允許連線至套件 registry，也可檢查已知安全性問題：

[source,bash]
----
pnpm audit
----

`audit` 結果仍需判斷實際使用路徑、套件用途與修正版本，不能只依嚴重度直接大範圍升版。

=== 9. 檢視異動

[source,bash]
----
git status --short
git diff -- package.json pnpm-lock.yaml pnpm-workspace.yaml
----

檢查重點：

* 是否只更新預期套件。
* 是否意外跨越大版號或加入 prerelease 版本。
* 是否新增陌生 registry、下載來源或 lifecycle script。
* `pnpm-workspace.yaml` 與 overrides、catalog、patched dependencies 是否仍一致。

=== 10. 提交異動

[source,bash]
----
git add package.json pnpm-lock.yaml pnpm-workspace.yaml
git diff --cached
git commit -m "chore: update frontend dependencies"
----

若專案沒有 `pnpm-workspace.yaml`，不要把不存在的檔案加入 Git。提交前應再次確認 staged diff 未包含 `.npmrc` Token、內部 registry URL 或其他機密資訊。

=== pnpm 指令速查

[cols="35%,65%", options="header"]
|===
|指令 |用途

|`pnpm outdated`
|查看可更新套件，不修改檔案。

|`pnpm update`
|依 `package.json` 的版本範圍更新依賴。

|`pnpm update <package> --latest`
|將指定套件更新至最新穩定版本，可能跨大版號。

|`pnpm install`
|安裝依賴，並確認 manifest 與 lockfile 的一致性。

|`pnpm install --frozen-lockfile`
|禁止變更 lockfile，適合 CI 驗證。

|`pnpm clean --lockfile`
|pnpm 11 清除 `node_modules` 與 lockfile，僅於必要時使用。

|`pnpm build`
|執行專案定義的 build script，不會更新套件。
|===

== npm 套件更新

=== 1. 確認執行環境

[source,bash]
----
node -v
npm -v
----

若 `package.json` 已設定 `engines` 或 `packageManager`，應使用專案指定的 Node.js 與 npm 版本，避免 lockfile 格式或依賴解析結果不一致。

=== 2. 查看可更新套件

[source,bash]
----
npm outdated
----

輸出中的 `wanted` 是符合 `package.json` 版本範圍的最高版本，`latest` 則是 registry 上標記為 `latest` 的版本。兩者不同時，通常代表最新版已超出目前允許的版本範圍。

需要檢查間接依賴時可使用：

[source,bash]
----
npm outdated --all
----

=== 3. 依既有版本範圍更新

[source,bash]
----
npm update
npm update vite
----

`npm update` 會依既有 semver 範圍更新套件。預設不改寫 `package.json` 內直接依賴的版本範圍；若要同步更新允許範圍，可使用 `npm update --save`，但仍應檢查實際 diff。

=== 4. 更新指定套件至最新版本

[source,bash]
----
npm install vite@latest
npm install react@latest react-dom@latest
----

此方式可能跨越大版號，且會修改 `package.json` 與 `package-lock.json`。應先確認 migration guide，並將核心框架升級與一般套件更新拆成不同次提交。

若要更新開發階段依賴，使用：

[source,bash]
----
npm install --save-dev vite@latest
----

=== 5. 安裝並驗證 lockfile

[source,bash]
----
npm install
npm ci
----

`npm install` 必要時會更新 `package-lock.json`；`npm ci` 要求既有 lockfile 與 `package.json` 一致，且不會修改兩者，適合模擬 CI 的乾淨安裝。

[NOTE]
====
`npm ci` 會先移除既有 `node_modules`。如果產生 lockfile 時使用了會影響依賴樹的設定，例如 `legacy-peer-deps`，CI 也必須使用相同設定。
====

=== 6. 執行品質與安全檢查

[source,bash]
----
npm run lint
npm test
npm run build
npm audit
----

實際可用命令取決於 `package.json` 的 scripts。不要直接使用 `npm audit fix --force` 處理所有問題，因為它可能安裝超出原版本範圍的套件並造成不相容變更。

=== 7. 檢視與提交異動

[source,bash]
----
git status --short
git diff -- package.json package-lock.json
git add package.json package-lock.json
git diff --cached
git commit -m "chore: update frontend dependencies"
----

提交前應確認 lockfile 沒有出現非預期 registry URL，且 `.npmrc` 未包含 Token、帳號或其他機密資訊。

=== npm 指令速查

[cols="35%,65%", options="header"]
|===
|指令 |用途

|`npm outdated`
|查看直接依賴的目前版本、允許版本與最新版本。

|`npm update`
|依既有 semver 範圍更新套件，預設不調整 `package.json` 的直接依賴範圍。

|`npm install <package>@latest`
|更新指定套件至 `latest`，可能跨大版號。

|`npm install`
|安裝依賴，必要時更新 lockfile。

|`npm ci`
|依 lockfile 執行乾淨安裝，不修改 manifest 與 lockfile。

|`npm audit`
|檢查 registry 提供的已知安全性問題。
|===

== Maven 依賴更新

=== 1. 確認執行環境

[source,bash]
----
java -version
mvn -version
----

若專案提供 Maven Wrapper，應優先使用 `./mvnw` 取代 `mvn`，以維持團隊與 CI 的 Maven 版本一致。

=== 2. 查看可更新版本

[source,bash]
----
mvn versions:display-dependency-updates
mvn versions:display-property-updates
mvn versions:display-plugin-updates
----

[cols="38%,62%", options="header"]
|===
|指令 |用途

|`versions:display-dependency-updates`
|檢查 `dependencies` 是否有新版，不修改 `pom.xml`。

|`versions:display-property-updates`
|檢查用來控制依賴或外掛版本的 `<properties>`，不修改 `pom.xml`。

|`versions:display-plugin-updates`
|檢查 Maven plugins 是否有新版，不修改 `pom.xml`。
|===

若版本定義在 parent POM、BOM 或公司內部 dependency management，顯示結果不一定等同於專案可直接採用的版本，仍需檢查繼承關係：

[source,bash]
----
mvn help:effective-pom
mvn dependency:tree
----

=== 3. 更新版本

風險最低的方式是一次手動調整一個 `pom.xml` 屬性或依賴版本，再執行驗證。若需要由 Versions Maven Plugin 修改指定屬性，可使用：

[source,bash]
----
mvn versions:update-property -Dproperty=套件版本屬性名稱
----

以下命令會直接將可處理的依賴更新到最新版本，可能跨越大版號：

[source,bash]
----
mvn versions:use-latest-versions
----

[WARNING]
====
`versions:use-latest-versions` 會修改 `pom.xml`，且預設允許 major、minor 與 incremental 更新。不要在未檢視結果時直接提交；多模組專案、BOM 與以 property 管理版本的專案尤其需要逐項確認。
====

Versions Maven Plugin 預設可能產生 `pom.xml.versionsBackup`。確認修改後可執行 `mvn versions:commit` 移除備份；若要放棄該次修改，可執行 `mvn versions:revert`。若專案已由 Git 管理，也可在確認沒有其他未提交異動後，使用 Git 精確回復相關檔案。

=== 4. 編譯與測試

[source,bash]
----
mvn clean verify
----

若專案有 profiles 或額外整合測試，應使用與 CI 相同的參數執行。更新 Java、Spring Boot、Maven plugin 或測試框架時，也要檢查最低 JDK 與 Maven 版本需求。

=== 5. 檢視與提交異動

[source,bash]
----
git status --short
git diff -- pom.xml
git diff -- '**/pom.xml'
----

多模組專案需檢查所有 `pom.xml`，並確認沒有提交 `target/`、本機設定檔、repository 帳密或 `settings.xml`。

[source,bash]
----
git add pom.xml
git diff --cached
git commit -m "chore: update Maven dependencies"
----

== Gradle 依賴更新

=== 1. 確認執行環境

[source,bash]
----
java -version
./gradlew --version
----

應優先使用專案內的 Gradle Wrapper（Linux、macOS 使用 `./gradlew`，Windows 使用 `gradlew.bat`），不要直接依賴開發機安裝的 `gradle` 版本。

=== 2. 查看目前依賴

Gradle 內建命令可以顯示已解析的依賴樹，但不會主動查詢每個套件的最新版本：

[source,bash]
----
./gradlew dependencies
./gradlew :app:dependencies
----

需要確認單一依賴的來源、版本衝突與選版原因時，可使用：

[source,bash]
----
./gradlew dependencyInsight \
  --dependency 套件名稱 \
  --configuration runtimeClasspath
----

`runtimeClasspath` 應依專案實際 configuration 調整，例如 `compileClasspath` 或測試相關 configuration。

=== 3. 檢查可更新版本

Gradle 沒有內建等同 `npm outdated` 的最新版檢查命令。若專案已設定 Gradle Versions Plugin，才可執行：

[source,bash]
----
./gradlew dependencyUpdates
----

[WARNING]
====
若出現 `Task 'dependencyUpdates' not found`，代表專案尚未設定該外掛。不要只為了執行一次檢查就任意修改正式建置設定；可先使用 IDE 的版本提示、套件 repository 或既有依賴更新機器人確認版本。
====

=== 4. 更新版本宣告

Gradle 不會透過 `dependencies` 或 `dependencyUpdates` 自動修改套件版本。應依專案管理方式調整下列檔案之一：

* `build.gradle` 或 `build.gradle.kts` 內的依賴版本。
* `gradle.properties` 內集中管理的版本屬性。
* `gradle/libs.versions.toml` 內的 version catalog。
* 平台專案、BOM 或 dependency constraints 的版本。

一次只更新一個核心框架或一組相關套件，並確認直接宣告版本與 Gradle 最終解析版本是否一致。

=== 5. 更新 dependency lock

只有已啟用 Gradle dependency locking 的專案才需要更新 lock state：

[source,bash]
----
./gradlew dependencies --write-locks
----

多模組專案需確認此命令是否解析到所有需要鎖定的 configurations。`gradle.lockfile` 應由 Gradle 產生並納入版本控制，不建議手動修改。

若只是懷疑本機 cache 過舊，可強制重新檢查遠端依賴：

[source,bash]
----
./gradlew build --refresh-dependencies
----

`--refresh-dependencies` 只重新檢查依賴 cache，不會自動將固定版本改成新版，也不應作為每次建置的預設參數。

=== 6. 編譯與測試

[source,bash]
----
./gradlew clean build
----

Android 或有自訂 task 的專案，應改用與 CI 相同的建置與測試 task。若更新 Gradle plugin、Kotlin、Android Gradle Plugin 或 Java toolchain，也要一併確認相容版本矩陣。

=== 7. 檢視與提交異動

[source,bash]
----
git status --short
git diff -- build.gradle build.gradle.kts settings.gradle settings.gradle.kts
git diff -- gradle.properties gradle/libs.versions.toml gradle.lockfile
----

只加入專案實際存在且本次有修改的檔案：

[source,bash]
----
git add build.gradle gradle.lockfile
git diff --cached
git commit -m "chore: update Gradle dependencies"
----

提交前確認沒有加入 `.gradle/`、`build/`、本機 repository 帳密或含機密資訊的 `gradle.properties`。

=== Gradle 指令速查

[cols="38%,62%", options="header"]
|===
|指令 |用途

|`./gradlew dependencies`
|顯示已解析的依賴樹，不檢查最新版。

|`./gradlew dependencyInsight ...`
|分析單一依賴的來源、衝突與選版原因。

|`./gradlew dependencyUpdates`
|使用已設定的 Gradle Versions Plugin 檢查可更新版本，不是內建 task。

|`./gradlew dependencies --write-locks`
|更新已啟用 dependency locking 的 lock state。

|`./gradlew build --refresh-dependencies`
|重新檢查依賴 cache，不會改寫固定版本。

|`./gradlew clean build`
|執行專案建置與測試，不會自動更新版本。
|===

== 建議更新順序

. 先更新 patch 版本並完成測試。
. 再更新 minor 版本，確認 deprecated API 與設定變更。
. major 版本分開處理，每次只升級一個核心框架或一組緊密相關套件。
. 重新執行完整建置、測試與必要的人工驗證。
. 檢視 manifest、lockfile、POM 與 staged diff 後再提交。
